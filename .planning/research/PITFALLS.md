# Thesis Revision Pitfalls & Mitigation Research

**Domain:** Undergraduate ML/NLP thesis report revision, post-defense
**Researched:** 2026-07-21
**Overall confidence:** MEDIUM-HIGH (grounded directly in the actual transcript; general guidance cross-checked against multiple independent sources but not against USTH-specific policy)

## Common Defense-Failure Patterns (methodology transparency)

**The core failure mode in the transcript is not "didn't do the work" — it's "couldn't produce evidence of the work on demand."** The judge asked some version of "how do you label them" roughly ten times, in escalating specificity (how did you label → where's the JSON → where's the class field → show me the dataset → how do 2000 samples map to labels), and each time the student either couldn't answer or found the artifact too slowly to satisfy the room. That gap — artifact exists somewhere in the repo, but is not a first-class, locatable, named section of the report — is a well-documented and common ML thesis failure pattern, not unique to this project.

- **Standard fix, beyond "explain it better": document the dataset like a component, not a footnote.** The "Datasheets for Datasets" framework (Gebru et al., widely cited standard in the ML community) prescribes a fixed set of questions any dataset section should answer: motivation, composition, collection process, **preprocessing/cleaning/labeling**, uses, distribution, maintenance. Applied here: an explicit subsection with (1) the JSON schema as a table, (2) a full concrete example record shown verbatim, (3) an explicit statement that labels are assigned *at generation time* (each synthetic sample is generated *for* a target class, not labeled after the fact), (4) the class definitions/boundaries. This is a **named, findable section**, not something inferable from code — the transcript failure was as much "unlocatable" as "unexplained."
- **This gap is common enough to be a known research finding, not a personal shortcoming**: peer-reviewed audits of ML papers ("Garbage In, Garbage Out?", repeated in a 2021 follow-up) found most published ML application papers fail to adequately report where human/generated training labels come from. Framing the fix as "closing a well-known reproducibility gap" (not "admitting the thesis was sloppy") is both accurate and the right tone for the revision.
- **Second pattern — missing explicit problem formalization.** The judge stated directly: "we are missing this in report, the Goal: Supervised classification" and "I didn't see the objective of classification here." Standard ML thesis structure expects an explicit, early problem-statement subsection: task type (supervised multi-class classification), input space, output space / label set (4 classes named), before the architecture section. Its absence is what let the whole "is this even classification?" line of questioning start — it's a structural gap, not a depth gap, and it's cheap to fix but was apparently entirely implicit in the current report.
- **Third pattern — missing architectural justification for an unusual choice.** The judge (an NLP-background examiner) explicitly proposed what they considered the "expected" design — encoder-style hidden representation + a downstream classification head — and asked why QLoRA fine-tuning a generative decoder-only model was used instead. Examiners routinely treat "why did you not use the standard/simpler approach" as a core methodology-understanding check in ML theses; not pre-empting it in the text reads as either not having considered alternatives or not understanding your own architecture. Standard fix: an explicit comparative rationale subsection (see Depth section below), not just a description of what was built.
- **Fourth pattern — internal numeric inconsistency triggers "did you actually run this" doubt.** The judge flagged that the confusion matrix / test-vs-validation counts didn't reconcile ("numbers like 15 here so it doesn't match with any... for 400 testing you did validation but doesn't match example here"). Cross-document numeric inconsistency (report vs. slides vs. tables) is a well-known signal examiners use to test whether results were actually produced by the student or partially borrowed/fabricated — it is functionally identical to a plagiarism/fabrication tell even when the underlying work is genuine, because inconsistency is what a copy-paste-without-understanding error looks like. This must be audited and reconciled, with an explicit note in-text about split sizes (train/val/test counts stated once, consistently, and referenced everywhere else).

## Demonstrating Ownership Without Changing Tone

The judge's own stated standard is the key data point here: *"I'm willing to accept AI-assisted drafting IF you can demonstrate genuine understanding."* This reframes the entire problem — the burden of proof is **evidentiary/content-level, not stylistic**. Style is what triggered scrutiny; content is what resolves it. This matches the convergent guidance found across academic-integrity and editorial-policy sources on AI-assisted scientific writing: the accepted standard is not "prove a human typed every word," it's "demonstrate the underlying reasoning, judgment, and verification are genuinely the author's," typically evidenced by disclosure of tool use plus traceable substance — not a stylistic purity test. No source found proposes "make it sound worse/rougher" as a legitimate strategy; all converge on content-level demonstration instead.

Practical content-level signals of genuine ownership — all addable in the existing voice, none requiring a rewrite:

1. **Traceable artifacts over assertions.** Every claim should point to something concrete and locatable: a schema table, a labeled appendix sample, a named file/table reference. This is literally what the judge was fishing for — "show me your dataset," "where is the JSON" — and a report that pre-answers "show me" with an actual example record removes the question before it's asked.
2. **Idiosyncratic, pipeline-specific detail rather than generic description.** Generic AI-generated methodology text tends to be *correct but non-specific* — it describes what fine-tuning generally involves, not what *this* pipeline specifically did. The antidote is maximally specific detail that only someone who ran the pipeline would know: the exact Pydantic quality-judge gate, the specific SHA-256 manifest step and why it exists, the specific class-boundary decisions, the specific generation-time labeling mechanism. Specificity is much harder to fake convincingly than fluent prose.
3. **Cross-document internal consistency.** One inconsistency (confusion matrix/test-val mismatch) is what helped trigger the "did you use ChatGPT" question in the first place. Consistency across report, tables, and slides is itself evidence of ownership, because reconciling numbers requires actually understanding what each of them means — it's a much harder thing to accidentally get right than fluent sentences.
4. **First-person worked-example walkthroughs.** A concrete, single-record walkthrough — from generation prompt/source through to the labeled JSON record to model input/output — written in first person ("I generate...", "each record is..."), demonstrates process fluency an outside drafting tool cannot produce without the author having actually built and inspected the pipeline.
5. **Explicit rejected-alternatives reasoning** (why not PhoBERT, why not a classification head) — comparative, decision-level reasoning that weighs concrete tradeoffs is harder to bluff than descriptive prose and is exactly the kind of "why" question the judge asked live and expects answered in text.

None of the above requires touching sentence-level style, vocabulary, or register — they are additive, specific, evidentiary paragraphs inserted into existing sections, written to match the surrounding voice (reuse `WRITING_GUARDRAILS.md`, as already planned). This is the correct strategy per the student's own constraint and is consistent with what the research surfaces as the accepted resolution path for this exact tension.

## Adding Genuine Depth vs. Padding

General guidance on legitimate expansion (dissertation/essay-writing sources) converges on: stronger evidence, deeper analysis of "how and why," concrete examples/case studies, and comparative/counter-perspective reasoning — as opposed to redundant repetition, tangential material, or filler transition language. Mapped onto this specific thesis's gaps, each planned addition should double as genuine reader-value, not page-count filler:

1. **Dataset/labeling section** (schema table + example record + generation-time labeling explanation) — required information the report currently lacks entirely; naturally dense, technical, non-fillable content. This alone plausibly adds 1–3 pages of real substance.
2. **Explicit problem-formalization subsection** — task type, input/output space, the 4 classes and why those specific classes reflect the real-world threat taxonomy in scope. Short (roughly half a page) but structurally load-bearing — it's the paragraph every downstream methodology decision should trace back to.
3. **Architecture rationale section** (generative decoder-only QLoRA vs. encoder + classification head) — a genuine comparative tradeoff discussion: e.g., a classification-head design would need a separate mechanism to produce the natural-language explanation/cues the system also outputs, while a single generative model can jointly emit label, grounded cues, and next-step guidance from one forward pass; conversely note the tradeoff cost (structured-output reliability, larger parameter count). This directly and substantively answers the judge's live question rather than just describing what was built — genuine depth, not filler, because it resolves an open technical question a reader would actually have.
4. **"Why Qwen, not PhoBERT" comparison, done properly.** The live answer (English-language extension) was weak and was directly undermined by the judge, who correctly pointed out the system's own scope is Vietnamese. The report version should instead be evidence-based: PhoBERT is an encoder-only model that produces embeddings, not free text — it cannot natively generate the required structured explanation/cues output without an added generation head, which reintroduces the architecture question above; an instruction-tuned generative model gives a single unified interface for label + explanation and better handles the code-switched Vietnamese–English scam text already in the project's stated scope. (Verify these specific technical claims against what is actually true for this project's data before writing — the goal is a defensible, evidence-based comparison, not a repeat of the contradiction that got caught live.)
5. **Error analysis with concrete worked failure cases.** Include 2–3 real misclassified validation/test examples with discussion of *why* — ambiguous class boundary, class imbalance, near-duplicate phrasing across classes, etc. This is standard expected depth in ML theses, is close to impossible to convincingly pad (a fake error analysis reads as generic immediately), and directly demonstrates the student understands their own results — pre-empting the "do you actually understand this" doubt category the whole defense turned on.
6. **Lightweight ablation-style discussion** (not necessarily a new training run given time constraints): explicitly discuss what a classification-head variant would change and why that path wasn't taken. This can be reasoned discussion citing the architecture-rationale section rather than a new experiment, and directly answers the judge's specific "why didn't you add classification layers" question.
7. **Confusion-matrix/split-count audit and fix** — not "depth" in the content sense, but correctness; pair the fix with one clear, explicit sentence stating train/val/test counts once and referencing it everywhere else in the report, removing the specific inconsistency that was flagged.

**Anti-pattern to avoid:** don't inflate sections that already work (e.g., the privacy/cloud-leakage motivation, which the record shows was already fine) — that reads as padding by definition (expansion disconnected from any open question) and dilutes the sections that matter.

## Distinguishing Genuine Revision From Padding (examiner perspective)

Signals that read as genuine, understanding-driven revision:
- New content is **dense with specific, checkable facts** — schema field names, exact counts, concrete example records — rather than restating known information in more words.
- New content **directly answers a question that was asked and left unanswered in the room.** A revision that closes exactly the six documented transcript gaps reads as responsive and targeted, not defensive bulk — examiners re-reading a revision are typically checking it against their own notes/questions first.
- **Internal consistency**, including consistency with the slides and any code/data artifacts already shown at defense — since the flagged inconsistency was itself part of what triggered suspicion, a revision that introduces no new inconsistencies (and visibly fixes the old one) is a direct integrity signal.
- **Traceability / willingness to show raw evidence** — appendix sample records, explicit schema, artifact references a skeptical reader could go verify — mirrors exactly what the judge asked for live ("show me your dataset") and is the strongest available de-padding signal because it's falsifiable, not merely descriptive.

Signals that read as padding (avoid):
- Redundant restatement of material already adequately covered elsewhere in the report.
- Vague hedging, throat-clearing, or transition language whose only function is length.
- Tangential related-work or background additions not tied back to a specific decision actually made in this thesis.
- Expanding whitespace, figure sizes, or table formatting instead of information density.

**Practical implication for page count:** the "~14 substantive pages, too short" complaint should be treated as a symptom, not a target. Closing the six content gaps (labeling section, problem framing, architecture rationale, Qwen-vs-PhoBERT, error analysis, consistency audit) will organically add pages because each is genuinely missing required content. If length is still short after all gaps are closed, the next lever should be *more depth inside those same sections* (e.g., additional worked failure-case examples) — never new, unrelated material added purely to hit a page number.
