<interfaces>
`RunEvent` is append-only and carries a monotonic event sequence, event kind, UTC timestamp, optimizer step, epoch, raw Trainer values, and source run ID. Adjacent events may share an optimizer step, but sequence IDs must be unique, contiguous, and preserved.

`RunEvidence` records the typed experiment identity, canonical train/validation identities, immutable model revision, resolved config/hash, formatter or preprocessor hash, the complete Qwen decoder contract/hash, sanitized argv, allowlisted environment/hardware details, quantization proof, raw event/prediction/trainer-state hashes, resource summaries, validation checkpoint metrics and selected-checkpoint rationale, model artifact hashes, graph provenance, status, and comparison eligibility. A Git identifier is not a required field.

`compare_qwen_configs(left, right)` uses exact equality for every controlled field, including `do_sample`, `num_return_sequences`, `max_new_tokens`, decoder schema/version, generation cadence, and raw-prediction ordering policy, with an explicit allowlist only for base-weight quantization proof differences. `compute_resume_digest` covers those decoder fields plus all other restart-controlled fields. No tolerance or dropped field is allowed.

`build_phase40_source_bundle(repo_root, output_root)` consumes a versioned explicit allowlist of runtime source/config paths, rejects symlinks and paths outside the repository before reading, writes a deterministic sorted inventory with per-file SHA-256, and produces a normalized archive whose bytes, inventory bytes, and file set reproduce identically from unchanged sources. `RunRequest` is an extra-forbid schema for exactly three fresh full identities, the three fixed returned-bundle roots, canonical input and model/config identities, one repository-relative hash-verified source archive plus its deterministic source-inventory manifest/hash, exact package candidates, expected complete bundle contents, step-zero origin, resume rules, and the no-held-out boundary. The code-artifact identity is the source-archive SHA-256 and inventory-manifest SHA-256; a Git commit identifier remains optional and is not required. `ColabOperatorReturn` is an extra-forbid in-memory schema containing exactly two approve/reject package decisions with optional sanitized reasons, exactly three canonical returned-root values when approved, and one normalized GPU identity per returned run; the finalizer persists its sanitized fields directly into the comparison manifest, so no checkpoint-owned authority file is implied. `verify_phase40_run_request` performs lexical root/input/source-archive checks before file access and verifies both source hashes before the archive is eligible for notebook extraction. `finalize_phase40_comparison` accepts only the three expected returned roots and sanitized human authority/hardware facts, verifies and rehashes every bundle, regenerates graphs, and atomically writes the comparison manifest plus Markdown report. The CLI commands `phase40-build-source-bundle`, `phase40-verify-run-request`, and `phase40-finalize-comparison` are implemented and fake-tested here before Plan 40-05 uses them; the latter accepts repeated typed `--package-decision`, `--bundle-root`, and `--gpu-identity` options or `--verify-only`, never a caller-selected output schema.

`build_phase40_input_bundle(contract, output_path)` accepts only the already-authorized immutable `Phase40DataContract` from Plan 40-01 and writes a deterministic stored ZIP with normalized metadata and exactly the sorted members `phase40-input-manifest.json`, `train.jsonl`, and `val.jsonl`. The two JSONL members are byte-for-byte the authorized canonical whole-file inputs; the canonical JSON manifest records schema version, exact member allowlist, logical names, record counts, whole-file SHA-256 values, Phase 39 manifest identity, and validation snapshot-ID algorithm/version. The archive cannot contain a reserved, test-like, absolute, traversal, symlink, directory, or extra member. `RunRequest.input_bundle` freezes the repository-relative archive path and SHA-256, manifest-member SHA-256, exact member list/counts/hashes, fixed Drive path `/content/drive/MyDrive/internship-phase40/phase40-train-validation.zip`, and fixed verified extraction root `/content/phase40-input-v1`; no laptop absolute path is serializable. `verify_phase40_input_bundle` first lexically accepts one of those request-bound local/Drive locations, then hashes the archive, inspects the ZIP directory, and verifies exact membership and manifest bytes before opening either JSONL member. Only after those gates does it stream/hash/count the two data members, extract them to fixed names under the verified root, and construct the same immutable snapshots/row IDs from the extracted bytes. A decoy path, extra/test-like member, manifest drift, member mutation, or path traversal causes zero train/validation member opens and no extraction. `verify_phase40_run_request` verifies both the source artifact and this input artifact before either is eligible for notebook use.

`ReviewQueueRow` is extra-forbid and contains `(model_run_id, validation_row_id)`, canonical validation sequence, immutable `raw_message`, `source_row_sha256` computed from the exact UTF-8 source JSONL record bytes excluding only its line terminator, gold label, predicted locked label or explicit `invalid_output`, selected-checkpoint/run/model-artifact identities, and the complete set of slice tags. `build_phase40_review_queue` accepts no caller-selected data path: it receives the selected-checkpoint predictions plus the already-authorized `Phase40DataContract` validation snapshot, requires exact stable-ID set/order equality, joins by ID, and proves the message/hash pair against the snapshot before writing. `phase40-verify-review-queue` repeats that binding against an already-preflighted validation snapshot, while `phase40-finalize-human-review` validates and atomically persists exact-coverage structured notes with a verify-only mode.
