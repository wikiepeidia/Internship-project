## Critical Issues

### CR-01: Suspicious-cue text is printed to the terminal without stripping ANSI/control characters (terminal escape injection)

**File:** `src/runtime/render.py:38,40,44` (sink), `src/runtime/cli.py:113` (print call), `src/runtime/analyzers/heuristic.py:47` and `src/runtime/analyzers/local_model.py:597-601` (source: raw user text)

**Issue:** The only text-cleaning step applied to a pasted message is
`normalize_text()` (`src/data_pipeline/core/text.py:32-37`), which repairs
mojibake, NFC-normalizes, and collapses whitespace — it does **not** strip C0
control characters or ANSI escape sequences (e.g. `\x1b[...`). That normalized
text is the exact string sliced to build `SuspiciousCue.span` in the heuristic
backend:

```python
# src/runtime/analyzers/heuristic.py
for match in rule.pattern.finditer(shadow_text):
    span = normalized_text[match.start() : match.end()]   # raw slice of user text
    ...
    ranked_matches.append((rule.weight, match.start(), SuspiciousCue(span=span, ...), ...))
```

For the local-model backends, `cue_span_is_grounded()` only requires the model's
reported span to be a case-insensitive substring of the same unsanitized
`normalized_text` (`src/runtime/analyzers/local_model.py:597-601`); it does not
reject control characters either. `_sanitize_recommendation_models()`
(`local_model.py:610`) only filters *unsafe advice content* ("click this link",
"share your OTP", etc.) — it has nothing to do with escape-sequence safety.

`AnalysisResult.summary`, `.top_cues[].span`, `.top_cues[].reason`, and
`.recommendations[]` all flow unmodified into `render_analysis_result()` and are
written straight to stdout via `print()` in `handle_analyze()`
(`src/runtime/cli.py:113`). A pasted phishing message containing raw ANSI escape
bytes (e.g. `\x1b[8m` to hide subsequent text, `\x1b]0;...\x07` to rewrite the
window/tab title, or vendor-specific sequences some terminal emulators
special-case) is therefore echoed byte-for-byte to the analyst's terminal. This is
exactly the kind of input this tool is designed to receive — attacker-controlled
Vietnamese phishing SMS/Zalo text pasted by the user — so the attack surface is
directly reachable via the documented `vnphish analyze` flow, not a contrived
edge case.

**Fix:** Strip or escape C0/C1 control characters (everything matching
`[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]` at minimum, and ideally the full ANSI CSI/OSC
escape grammar) before any user-derived string reaches `print()`. The cleanest
place is a dedicated `sanitize_for_terminal()` helper applied in
`render_analysis_result()`/`render_runtime_error()` immediately before joining
lines, e.g.:

```python
import re
_CONTROL_CHARS = re.compile(r"[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]")

def _terminal_safe(text: str) -> str:
    return _CONTROL_CHARS.sub("", text)
```//and apply `_terminal_safe(...)` to `result.summary`, each `cue.span`/`cue.reason`,
each threat-label display string, and each recommendation before formatting.

### CR-02: `/api/analyze` on the local demo server has no CSRF/Origin protection

**File:** `src/runtime/demo.py:98-149` (`DemoApp._handle_analyze`), `src/runtime/demo.py:173-192` (`run_demo_server`)

**Issue:** `run_demo_server()` binds only to a loopback address (enforced by
`require_loopback_host`), which correctly prevents remote-network exposure. But
the WSGI handler for `POST /api/analyze` never checks the `Origin` or `Referer`
header, never validates `Content-Type`, and the server sets no
`Access-Control-Allow-Origin` (or any CORS) headers at all:

```python
def _handle_analyze(self, environ, start_response):
    try:
        content_length = int(environ.get("CONTENT_LENGTH") or 0)
        ...
        raw_body = environ["wsgi.input"].read(content_length) if content_length else b"{}"
        payload = json.loads(raw_body.decode("utf-8"))
        ...
```

Because `Content-Type` is never inspected, a third-party web page the operator
happens to have open in the same browser while `vnphish demo` is running can
issue a same-"simple-request" cross-origin `fetch()` (e.g.
`Content-Type: text/plain`, which avoids a CORS preflight) whose body is valid
JSON, and the browser will still send it to `http://127.0.0.1:8765/api/analyze`.
The browser blocks the attacker page from *reading* the JSON response (no ACAO
header), but the request still executes server-side — the model/backend still
runs `analyze_text()`, which per `RuntimeService.analyze_text` can trigger a full
GGUF/accelerated model load and inference pass. A malicious page can loop this
to force repeated model warm-ups/inference (local resource-exhaustion / DoS via a
drive-by page), and in the accelerated-backend case (`AcceleratedAnalyzer`, see
WR-01) each of those forced requests also re-triggers full artifact
re-verification and model construction, not just inference.

This matches the "loopback demo request protections" item your own `CLAUDE.md`
architecture debt list names, and is confirmed still present in the current
`src/runtime/demo.py`.

**Fix:** Reject the request unless the `Origin` (or, if absent, `Referer`) header
exactly matches the server's own loopback origin, e.g.:

```python
def _handle_analyze(self, environ, start_response):
    origin = environ.get("HTTP_ORIGIN")
    expected = f"http://{environ.get('HTTP_HOST', '')}"
    if origin is not None and origin != expected:
        return _json_response(start_response, "403 Forbidden",
                               {"error": {"message": "Cross-origin requests are not allowed.", "steps": []}})
    ...
```

and/or require a `Content-Type: application/json` check (which forces a CORS
preflight for cross-origin browser requests and lets you reject anything that
isn't same-origin) in addition to the Origin check, since either alone is a
weaker defense than both together.

## Warnings

### WR-01: `AcceleratedAnalyzer.doctor()` does not cache readiness, unlike `GGUFAnalyzer`

**File:** `src/runtime/analyzers/accelerated.py:169-280` (no `_cached_doctor_status`), contrast with `src/runtime/analyzers/gguf.py:126-239` (`if status.ready: self._cached_doctor_status = status`)

**Issue:** `RuntimeService.analyze_text()` unconditionally calls
`self.backend.doctor()` on every request when `runtime_fail_closed` is true
(the default — see `src/runtime/service.py:116-121`). `GGUFAnalyzer` caches a
successful `DoctorStatus` so repeated requests skip the registry-load +
artifact-verification + runtime-load path. `AcceleratedAnalyzer` has no such
cache field at all, so every single `analyze()` call re-loads the model
registry, re-verifies both the adapter and base-model artifact identities, and
re-enters `_load_runtime()` (which only short-circuits the actual
tokenizer/model construction if the resolved artifacts are unchanged, but still
pays the registry read + SHA-256 re-verification cost every time). Combined with
CR-02, this asymmetry increases the effectiveness of the drive-by request issue
for accelerated-profile deployments.

**Fix:** Give `AcceleratedAnalyzer` the same successful-status caching contract
`GGUFAnalyzer` uses, or move the caching decision into `RuntimeService` so both
backends share one doctor-caching policy instead of each backend re-implementing
(or not implementing) it.

### WR-02: Dead trimming logic in `RuntimeService.analyze_text()`

**File:** `src/runtime/service.py:142-143`

**Issue:**

```python
if len(result.top_cues) > self.settings.runtime_max_cues:
    result = result.model_copy(update={"top_cues": result.top_cues[: self.settings.runtime_max_cues]})
```

`AnalysisResult.top_cues` already carries a hard `max_length=3` Pydantic
constraint (`src/runtime/contracts.py:50`), and `RuntimeDoctor` treats
`runtime_max_cues == 3` as a mandatory readiness check
(`src/runtime/doctor.py:92-97`: `passed=settings.runtime_max_cues == 3`). Given
`runtime_fail_closed` is also enforced by default, this branch can only ever be
reached with `len(result.top_cues) <= 3 == self.settings.runtime_max_cues`, so
the condition is always false in a "ready" runtime — this is unreachable/dead
code that exists to guard against an invariant the doctor check has already made
impossible to violate.

**Fix:** Either remove the branch (relying on the Pydantic field constraint), or
decouple the invariant — stop hard-failing doctor when `runtime_max_cues != 3`
and let this trimming logic be the actual enforcement point, whichever is the
intended design.

### WR-03: `GGUFAnalyzer._allowed_profiles()` silently collapses on a profile-name collision

**File:** `src/runtime/analyzers/gguf.py:51-56`

**Issue:**

```python
def _allowed_profiles(self) -> dict[str, str]:
    settings = get_settings()
    return {
        settings.runtime_profile_gguf: "baseline_winner_id",
        settings.runtime_profile_gguf_runner_up: "runner_up_id",
    }
```

If `runtime_profile_gguf` and `runtime_profile_gguf_runner_up` are ever
configured to the same string (e.g. via a misconfigured `.env` override — nothing
in `RuntimeSettings` validates that the two are distinct), this dict collapses to
a single entry and the runner-up profile silently disappears instead of raising a
configuration error. `doctor()`'s `runtime-profile` check
(`passed=self.runtime_profile in allowed_profiles`) would still report success
for whichever profile happens to remain, masking the misconfiguration.

**Fix:** Add a `model_validator` on `RuntimeSettings` (or a targeted
field-combination check) that rejects `runtime_profile_gguf ==
runtime_profile_gguf_runner_up`.

### IN-01: `scripts/archive_phase41_source_closure.py` re-exports private (`_`-prefixed) symbols from `src.source_archiving`

**File:** `scripts/archive_phase41_source_closure.py:39-71`

**Issue:** The compatibility shim imports and re-exports numerous underscore-prefixed
"private" names from `src.source_archiving` (e.g. `_ArchiveLayout`,
`_CapturedClosure`, `_PublicationBinding`, `_canonical_json`, `_sha256`, ...)
purely so historical/test callers can keep referencing them through the old
module path. This is intentional per the module's docstring
("Compatibility aliases intentionally expose the former module surface..."), so
it is not a defect, but it does mean `src.source_archiving`'s underscore-prefixed
names are not actually private from an external-caller standpoint — any future
refactor of those internals in `contracts.py`/`filesystem.py`/`service.py` must
also update this shim or it will silently go stale (there is a test,
`test_source_archiving.py`, that should catch drift, but it wasn't opened in this
pass to confirm coverage).

**Fix:** No action required if intentional; consider a short comment in
`src/source_archiving/contracts.py`/`filesystem.py`/`service.py` noting that
these underscore names are pinned compatibility surface for the script shim, so
future maintainers don't rename them casually.

### IN-02: `HeldOutSupportAudit`/`ReleaseEvaluationArtifact` recompute-and-overwrite pattern relies on `model_fields_set` ordering

**File:** `src/artifacts.py:277-294`

**Issue:** `align_status_with_blockers()` conditionally validates
`blocker_reasons`/`ready`/`verdict` against `self.model_fields_set` only when the
caller explicitly supplied those fields, then unconditionally overwrites them
with the computed values at the end of the same validator. This is defensible
(it means "if you passed a mismatched value, fail; otherwise, fill it in for
you"), but it's a subtle pattern — a caller who supplies `blocker_reasons` that
happen to match by coincidence but supplies a stale `ready`/`verdict` would still
be silently corrected rather than rejected as inconsistent with *itself*
(`ready`/`verdict`/`blocker_reasons` are cross-checked against the computed
value, not against each other before the overwrite). No incorrect behavior was
found, but a future contributor extending this validator should keep the
"supplied-then-overwritten" order in mind — reordering the checks could silently
change which mismatches raise.

**Fix:** No code change requested; noting for future maintainers.
