## Iteration 2 — Fixed Issues

### WR-N1: `runtime_max_cues` clamp was unenforced on the demo server path

**File modified:** `src/runtime/service.py`
**Commit:** `187fedf`
**Applied fix:** The iteration-1 WR-02 fix removed `RuntimeService.analyze_text()`'s cue-trimming
branch on the theory that `RuntimeDoctor.run()`'s `runtime_max_cues == 3` readiness check made it
unreachable. The re-review traced the call graph and found that's only true for the CLI path
(`cli.py::handle_analyze`/`handle_doctor`) — `DemoApp._handle_analyze -> RuntimeService.analyze_text`
never calls `RuntimeDoctor.run()`, so an operator running the demo server with `RUNTIME_MAX_CUES`
set below 3 got unclamped `top_cues` output. Restored the clamp as
`max_cues = max(0, min(self.settings.runtime_max_cues, 3)); if len(result.top_cues) > max_cues: ...`
— this both re-enforces a sub-3 operator override on the demo path and guards against a
above-3 override (the `min(..., 3)` term), on top of `AnalysisResult.top_cues`'s existing
`max_length=3` Pydantic ceiling. Verified: `tests/runtime/test_render.py` +
`tests/runtime/test_demo.py` 14/14 passed; `tests/runtime/test_service.py`'s 5 pre-existing
failures (unrelated `model_artifact_root must be below model_storage_root` local environment
issue, same as documented in iteration 1) reproduce identically before and after this change.

### WR-N2: Residual raw carriage-return spoof vector in ungrounded model-output fields

**File modified:** `src/runtime/render.py`
**Commit:** `d2dce5e`
**Applied fix:** Iteration 1's `_CONTROL_CHARS` regex excluded `\x0d` (CR) alongside `\t`/`\n` on
the assumption all rendered fields are pre-normalized. That's true for `cue.span` (grounded via
`normalize_text()`), but `summary`, cue `reason`, and `recommendations` text come directly from
structured-output model generation and are not substring-grounded — an ungrounded backend can
still emit a raw `\r`, which is a same-line cursor-return spoof vector (e.g. overwriting
"SUSPICIOUS" with "ALL CLEAR" on redraw). Changed `_CONTROL_CHARS` from
`[\x00-\x08\x0b\x0c\x0e-\x1f\x7f-\x9f]` to `[\x00-\x08\x0b-\x1f\x7f-\x9f]` — this folds `\x0c`
into the already-excluded-from-`\t`/`\n` range and now strips `\x0d` unconditionally, while still
leaving `\t`/`\n` (`\x09`/`\x0a`) untouched. Verified: `tests/runtime/test_render.py` 2/2 passed
(byte-identical output for the non-hostile case, same as iteration 1's own verification).

### WR-N3: CR-02's Origin/Referer/Content-Type rejection paths had zero test coverage

## Fixed Issues

### CR-01: Suspicious-cue text is printed to the terminal without stripping ANSI/control characters

**Files modified:** `src/runtime/render.py`
**Commit:** `b724324`
**Applied fix:** Added a `_terminal_safe()` helper in `src/runtime/render.py` that strips C0
control characters, DEL, and C1 control characters (`[\x00-\x08\x0b\x0c\x0e-\x1f\x7f-\x9f]`,
which covers the byte range ANSI CSI/OSC escape sequences rely on) and applied it to every
user-derived string before it is joined into the rendered output: `result.summary`, each
threat-label display string, each `cue.span`/`cue.reason`, and each recommendation in
`render_analysis_result()`, plus `message`/`step` strings in `render_runtime_error()`. Both
functions are the last step before `src/runtime/cli.py:113`'s `print()` call, so this closes the
sink identified in the finding without touching the analyzer/source files (`heuristic.py`,
`local_model.py`) that the finding cited only as illustrating the taint path. Verified with
`tests/runtime/test_render.py` (2/2 passed) — existing rendering behavior for the non-hostile
case is byte-identical.

### CR-02: `/api/analyze` on the local demo server has no CSRF/Origin protection

**Files modified:** `src/runtime/demo.py`
**Commit:** `8d09faf`
**Applied fix:** Added `_expected_origin()` and `_is_same_origin_request()` helpers to
`src/runtime/demo.py` and call them at the top of `DemoApp._handle_analyze()` before any body
parsing: (1) reject any request whose `Content-Type` is not exactly `application/json` (adapted
from the review's suggestion — this alone forces a CORS preflight for real cross-origin
`fetch()` calls, closing the `text/plain` "simple request" bypass called out in the finding), then
(2) reject the request with `403 Forbidden` if an `Origin` header is present and does not match
`http://{Host}`, or if no `Origin` is present but a `Referer` header is present and does not match
that origin. Requests with neither header (e.g. `curl`, non-browser automation) are allowed
through unchanged, matching the review's suggested logic (`if origin is not None and origin !=
expected: reject`). Verified with `tests/runtime/test_demo.py` (7/7 passed) — all existing demo
tests send `Content-Type: application/json` and no `Origin`/`Referer`, so none needed adaptation.

### WR-01: `AcceleratedAnalyzer.doctor()` does not cache readiness, unlike `GGUFAnalyzer`

**Files modified:** `src/runtime/analyzers/accelerated.py`
**Commit:** `3bac7d4`
**Applied fix:** Added a `_cached_doctor_status: DoctorStatus | None` dataclass field to
`AcceleratedAnalyzer`, mirroring `GGUFAnalyzer` exactly: `doctor()` now returns the cached status
immediately if set, and caches the computed `DoctorStatus` only when `status.ready` is `True`
(a failed/not-ready status is never cached, so re-checks after a registry/artifact fix are still
picked up). This gives both backends the same doctor-caching contract, closing the asymmetry the
finding flagged as compounding CR-02's drive-by-request risk for accelerated-profile deployments.
Ran `tests/runtime/test_accelerated_backend.py`: 3 pre-existing failures were confirmed present
identically before and after this change (`git stash` diff test) — they are caused by a
`FakeSettings` object in those tests missing a `resolved_model_artifact_root` attribute, unrelated
to this fix.

### WR-02: Dead trimming logic in `RuntimeService.analyze_text()`

**Files modified:** `src/runtime/service.py`
**Commit:** `1be3a84`
**Applied fix:** Removed the `if len(result.top_cues) > self.settings.runtime_max_cues:` trimming
branch in `RuntimeService.analyze_text()`, relying instead on the `max_length=3` Pydantic
constraint already on `AnalysisResult.top_cues` (`src/runtime/contracts.py`), per the review's
first suggested remedy. **Note for human verification:** while investigating this finding I traced
that the `demo.py` request path (`DemoApp._handle_analyze` -> `RuntimeService.analyze_text`) does
*not* route through `RuntimeDoctor.run()` (which is the only place that hard-enforces
`runtime_max_cues == 3`) — it only calls the backend-level `doctor()`, which never inspects
`runtime_max_cues`. So the removed branch was not strictly unreachable in all code paths the way
the review's blocker-invariant argument assumed; it only ever mattered if an operator misconfigured
`runtime_max_cues` below 3 (default is 3), and even then the field constraint already caps
`top_cues` at 3, so no more-than-3-cues leak was ever possible — only a smaller
operator-configured limit would have been silently unenforced by this specific line. Flagging this
distinction so a human can confirm the intended behavior for a misconfigured `runtime_max_cues`
override is acceptable before treating this as fully closed.
