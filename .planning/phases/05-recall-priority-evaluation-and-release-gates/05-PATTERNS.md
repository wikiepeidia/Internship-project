# Phase 5: Recall-Priority Evaluation and Release Gates - Patterns

## Summary

Phase 5 should treat [src/runtime/contracts.py](src/runtime/contracts.py) and [src/runtime/service.py](src/runtime/service.py) as the stable measurement boundary, then put new offline evaluation and release-gate code under [src/model_adaptation](src/model_adaptation). The closest repo patterns are deterministic recall-first scoring in [src/model_adaptation/pilot.py](src/model_adaptation/pilot.py#L25), typed shared metadata in [src/model_adaptation/schemas.py](src/model_adaptation/schemas.py), typed JSON persistence in [src/model_adaptation/registry.py](src/model_adaptation/registry.py#L39) and [src/data_pipeline/versioning/manifest.py](src/data_pipeline/versioning/manifest.py#L13), concise operator output in [src/model_adaptation/cli.py](src/model_adaptation/cli.py), [src/model_adaptation/doctor.py](src/model_adaptation/doctor.py#L308), and [src/runtime/render.py](src/runtime/render.py#L20), and phase-document naming from [04-01-PLAN.md](.planning/phases/04-threat-detection-and-explainable-decisioning/04-01-PLAN.md), [04-01-SUMMARY.md](.planning/phases/04-threat-detection-and-explainable-decisioning/04-01-SUMMARY.md), and [04-VALIDATION.md](.planning/phases/04-threat-detection-and-explainable-decisioning/04-VALIDATION.md).

The strongest location signal is that Phase 5 is an offline, batch-style evaluation slice over already-stable runtime outputs, not a new runtime subsystem. The planner should therefore extend the existing model-adaptation workflow and only touch runtime surfaces when Phase 5 needs a narrow operator-facing summary.

The strongest existing naming pattern is `manifest-<version_tag>.json`, as seen in [data/manifests/manifest-phase1-recovered-balanced-claude-v2.json](data/manifests/manifest-phase1-recovered-balanced-claude-v2.json) and [src/data_pipeline/versioning/build.py](src/data_pipeline/versioning/build.py#L33).

## Public Seams and Patterns To Preserve

- Preserve the Phase 4 measurement boundary. Evaluate the shipped [AnalysisResult](src/runtime/contracts.py) surface, not backend-private raw model payloads or temporary prompt schema internals.
- Preserve recall-first policy. [src/model_adaptation/pilot.py](src/model_adaptation/pilot.py#L25) and [src/model_adaptation/pilot.py](src/model_adaptation/pilot.py#L115) already encode recall as the dominant safety signal; Phase 5 gates should extend that policy into blocking logic instead of replacing it with a balanced average.
- Preserve typed shared models. The repo consistently uses Pydantic models at cross-module seams in [src/model_adaptation/schemas.py](src/model_adaptation/schemas.py), [src/data_pipeline/schemas.py](src/data_pipeline/schemas.py), and [src/runtime/contracts.py](src/runtime/contracts.py). Phase 5 should do the same for metrics, verdicts, and report payloads.
- Preserve explicit JSON persistence style. Use parent-directory creation plus formatted JSON writes as in [src/model_adaptation/registry.py](src/model_adaptation/registry.py#L39), [src/data_pipeline/versioning/manifest.py](src/data_pipeline/versioning/manifest.py#L65), and [src/model_adaptation/training.py](src/model_adaptation/training.py#L508).
- Preserve thin CLI surfaces. Existing CLIs parse args, call helpers, and print concise summaries rather than embedding business logic in the parser file. Keep Phase 5 evaluation commands equally thin.
- Preserve inline, local tests. Existing tests create small typed records in code and use `tmp_path` to stage files. Avoid introducing committed fixture corpora unless Phase 5 truly needs them.
- Preserve offline and local-first constraints. Phase 5 context explicitly prefers deterministic checks plus a curated manual sample; do not center the design on cloud judging or hosted evaluation services.

## Anti-Patterns

- Putting the main evaluator under `src/runtime/` or `src/runtime/analyzers/`. That would blur the repo's boundary between live inference and offline model-adaptation workflows.
- Writing the machine-readable release JSON under `.planning/` or `docs/`. Existing machine artifacts live under [data/manifests](data/manifests).
- Writing the human-readable markdown release report under `data/manifests/`. The context explicitly separates machine artifacts from planning-folder markdown, and Phase 4 already follows that split.
- Creating a new top-level `tests/evaluation/` package. Repo tests are organized by owning domain package, so Phase 5 evaluation tests should live under [tests/model_adaptation](tests/model_adaptation) unless they directly change runtime operator surfaces.
- Recomputing evaluation labels from backend-private raw payloads instead of measuring the contract-stable runtime outputs. Phase 5 is supposed to evaluate the shipped surface that Phase 4 locked.
- Hiding blocker reasons inside one aggregate score. Existing repo patterns favor explicit fields, explicit notes, and explicit remediation commands.
- Letting CLI-only strings become the source of truth for verdicts or metrics. Verdicts and per-class metrics should come from typed models first, then be rendered to JSON, markdown, or terminal text.
