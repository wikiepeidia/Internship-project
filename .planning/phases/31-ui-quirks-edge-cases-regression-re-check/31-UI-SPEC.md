# Phase 31 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Phase Type: Regression Lock + Conditional Quirk Fix (NOT new visual design)

Phase 31 re-tests an **already-shipped** chat UI (built v2.0, Phases 14-18; hardened Phase 29 for offline/font self-hosting). It does not introduce new screens, components, colors, spacing, or typography. This document's job is:

1. **Catalogue the existing, frozen design system** (grounded in the real `index.html` / `demo.css` / `demo.js` / `i18n.js` source, not placeholders) so nothing gets reinvented.
2. **Declare the regression acceptance bar** for UIQ-01 (edge-case matrix) and UIQ-02 (double-submit) — what "no crash, no hang, no regression" means concretely for this UI.
3. **Constrain any UIQ-04 fix** (including the `ERROR SOURCE_LANG_VI` console mystery from `29-04-SUMMARY.md`, D-01) to reuse existing tokens/patterns rather than introduce anything new.

**Out of scope for this document:** UIQ-03 (CLI `--help` text and `.bat` launcher scripts) touches `src/runtime/cli.py` and `scripts/*.bat` only — it has no browser-rendered surface and is not a UI-SPEC concern.

**Hard constraint carried from STATE.md:** no JS frameworks, no build step (vanilla HTML/CSS/JS only) — the shadcn initialization gate does not apply to this project (see Design System section). Backend `/api/analyze` contract and `data-slot` template internals are frozen and must not change as a side effect of any fix in this phase.

## Spacing Scale

**This phase does not retrofit a strict 4/8-point token system.** The shipped `demo.css` (Phase 14/16/17) uses hand-tuned values in the 5–24px range, chosen per component, not a formal scale. The table below anchors real shipped values to the nearest 8-point bucket for reference only — it documents what exists, it does not prescribe new values.

| Token | Nearest shipped value(s) | Real usage (verbatim from `demo.css`) |
|-------|---------------------------|----------------------------------------|
| xs (~4px) | 5px | `.typing-dots { gap: 5px }`; `.message__meta { margin: 0 0 5px }` |
| sm (~8px) | 7-8px | `.status-strip, .hint-row { gap: 8px }`; `.detail-list li + li { margin-top: 7px }`; `select { padding: 8px 10px }` |
| md (~16px) | 14-17px | `.message { margin: 0 0 16px }` (inter-bubble spacing); `.message__bubble { padding: 15px 17px }`; `.composer-panel { padding: 14px 16px ... }` |
| lg (~24px) | 22px | `.chat-thread { padding: 22px }`; `.composer-panel { margin: 0 22px }` |
| xl (~32px) | not used | no shipped rule uses a ~32px value anywhere in `demo.css` |
| 2xl (~48px) | not used | no shipped rule uses a ~48px value |
| 3xl (~64px) | not used | no shipped rule uses a ~64px value |

**Exceptions (pre-existing, frozen — not to be normalized this phase):** 5px, 7px, 10px, 12px, 13px, 14px, 15px, 17px, 18px, 22px all appear as deliberate hand-tuned values from Phase 14/16/17. Touch targets already meet the 44px minimum where interactive (`.primary-button`/`.secondary-button` `min-height: 44px`, `select { min-height: 44px }`).

**Rule for any UIQ-04 fix:** reuse the exact spacing value already used by the nearest sibling/parent element being touched. Do not introduce a new arbitrary spacing number.

**This documents an already-shipped system (more than the standard 3-4 size / 2 weight new-design guideline) because it is inherited, tested, and frozen — not new design.** Do not add a 5th size or a 3rd/4th weight without a specific measured quirk that requires it.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (message text, default page text) | 16px / `1rem` (15px on ≤460px viewport) | 400 regular (implicit — no `font-weight` set) | 1.65 |
| Label (meta text, form labels, status/hint pills, eyebrow) | 12px / `0.78rem` (meta, eyebrow, pills) and 14px / `0.86rem` (field labels, `detail-section` headings) | 700 bold (explicit) | ~1 (single-line labels; inherits body 1.65 but visually single-line) |

## Regression Acceptance Bar (Phase 31 specific)

Concrete, testable assertions for "no crash or hang" (UIQ-01) and "guard still works" (UIQ-02), against the existing UI described above. These are the pass/fail criteria the planner should turn into test assertions and the executor should verify manually/via Playwright.

### UIQ-01 — Edge-case matrix (empty, very long, malformed/off-topic, mixed VI-EN)

- **Empty input:** the native `required` attribute on `#message-input` blocks a true empty submit client-side (browser validation bubble) — no bot/error bubble should be created. If any future change bypasses `required` (e.g., a programmatic submit path), the app must surface a bilingual message via the existing `error-template` pattern, not a silent no-op or a thrown JS exception.
- **Very long text:** the bot bubble must stay within the existing `.message__bubble { max-width: min(760px, calc(100% - 46px)) }` constraint; long unbroken tokens (e.g., a URL inside a grounded cue) must wrap rather than overflow horizontally (matches existing `.meta-grid dd { overflow-wrap: anywhere }` pattern — apply the same treatment if a new long-text container is touched). The composer `textarea` caps growth at `max-height: 28dvh` with internal scroll and must not push the send button off-screen.
- **Malformed / off-topic text:** must always resolve to either a rendered bot bubble (via `result-template`) or a well-formed error bubble (via `error-template`) — never a raw unhandled JS exception in the console, never an orphaned typing indicator left in `#result-panel`.
- **Mixed Vietnamese-English text:** must render through Be Vietnam Pro without diacritic stacking/clipping in both the user bubble (navy/teal gradient, white text) and bot bubble (white panel, ink text) — enforced by the locked line-height ≥1.65 rule above.
- **In every case above:** the typing indicator (`.message--typing`, cloned from `typing-template`) must be removed (`typingEl.remove()`) before the terminal bubble (result or error) renders — zero orphaned typing nodes after the request settles, for every input class tested.
- **Empty-list rendering:** when `grounded_cues`, `recommendations`, or `threat_labels` come back empty (plausible for malformed/off-topic input), the existing `LIST_EMPTY` fallback copy "Không có" must render — not a blank `<ul>`, not a JS error from `createListItems`.

### UIQ-02 — Rapid double-submit / `AbortController` guard

- Exactly one visible bot/error bubble must result per logical user turn — never two bubbles for one rapid double-click.
- `currentController.abort()` (in `demo.js`) must fire before the second `fetch()` starts; the aborted request's `catch` branch must swallow `AbortError` silently — no error bubble may render for the superseded request.
- Exactly one typing indicator may be present/settle at a time — no duplicate `.message--typing` nodes stacked in the thread.
- `#analyze-button` busy-state (`disabled` + `ANALYZE_BTN_BUSY` label) must correctly clear after the surviving request settles — it must not get stuck disabled if the first (aborted) request's `finally` block races the second request's `finally` block.

### UIQ-04 — Constraints on any fix (including the `ERROR SOURCE_LANG_VI` triage per CONTEXT.md D-01)

- Triage protocol (already decided, D-01): reproduce first; if it traces to real app code, fix as a quirk under the constraints below; if confirmed non-app browser/extension noise, document and stop — no open-ended root-cause hunt.
- Any code-level fix must:
  - Reuse existing CSS custom properties and classes — no new hex color, no new font size/weight, no new spacing constant (see Spacing/Typography/Color sections above).
  - Keep all `<template>` internals identified by `data-slot` — never add an `id` to cloned template content (the exact pitfall Phase 14 fixed).
  - Leave the `/api/analyze` request/response shape unchanged.
  - Add any new user-facing copy as a new key in `i18n.js` only — never hardcode a string into `index.html` or template markup (I18N-02). New copy follows the existing bilingual pattern: Vietnamese-primary, with an English technical term in parentheses only when the string names a risk/technical concept (e.g., `"Nguy hiểm cao (High risk)"`); plain operational copy (like existing `ERR_NETWORK_STEP`) does not need an English gloss.
  - Introduce zero new dependencies (no icon library, no JS framework, no build step).
- Re-run `tests/runtime/test_local_model.py` and `tests/runtime/test_demo.py` (per CONTEXT.md D-05) after any fix, plus the Phase 28 golden-prompt regression check, before considering UIQ-04 closed.

## Copywriting Contract

All copy below is already shipped in `src/runtime/demo_assets/i18n.js` — documented here so it is confirmed, not re-invented, and so any new string added under UIQ-04 follows the same pattern.

| Element | Copy |
|---------|------|
| Primary CTA | `ANALYZE_BTN`: "Phân tích tại máy" (Analyze on this device); busy state `ANALYZE_BTN_BUSY`: "Đang phân tích..." (Analyzing...) |
| Empty state heading | No discrete "empty state" screen exists — the thread always contains the pre-rendered welcome bubble at page load (ARIA-live requirement from Phase 14). Heading equivalent: `WELCOME_ASSISTANT_NAME`: "Trợ lý kiểm tra" |
| Empty state body | `WELCOME_TEXT`: "Mình sẽ giúp bạn kiểm tra dấu hiệu lừa đảo tài chính." + hint-row chips (`HINT_SMS`/`HINT_ZALO`/`HINT_MESSENGER`/`HINT_NO_CLOUD`). For an empty **list** inside a result bubble (zero cues/recommendations/labels), the relevant copy is `LIST_EMPTY`: "Không có" |
| Error state | `ERROR_META`: "Phản hồi runtime" (heading) + `ERR_NETWORK`: "Không thể kết nối với runtime cục bộ." (problem) + `ERR_NETWORK_STEP`: "Thử lại sau khi runtime cục bộ đã tải xong." (next step), rendered via `error-template`/`appendErrorBubble`. Non-network errors (4xx/5xx) use the server-supplied `payload.error.message` + `payload.error.steps[]` through the same template. |
| Destructive confirmation | `CLEAR_BTN`: "Xóa" (Clear) — single click, **no confirmation dialog** (existing shipped behavior, Phase 17 POLISH-02). Low-stakes by design: chat history is in-memory only (no `localStorage`, no server mutation), so an accidental clear has no data-loss consequence beyond re-typing. Not to be changed this phase unless UIQ-01/02/04 testing surfaces a concrete problem (e.g., accidental clear during a live-demo-critical moment) — currently undecided, Claude's/planner's discretion per CONTEXT.md. |
