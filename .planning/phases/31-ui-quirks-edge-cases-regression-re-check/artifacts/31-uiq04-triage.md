## Finding 2: `very_long` case returns HTTP 503 (`RuntimeUnavailableError`)

- **Classification: backend-origin, frozen this milestone — documented, not fixed.**
- **What happens:** The bounded `very_long` fixture (12 repeated sentences + one long unbroken URL token, deliberately built to be large but finite) is submitted through the real form. `RuntimeService.analyze_text()` calls `self.backend.analyze(request)`, which raises an exception from the GGUF backend (the prompt plus the long input text exceeds the runtime's configured `n_ctx=512` context window — the doctor/server startup log for this exact run shows `llama_context: n_ctx_seq (512) < n_ctx_train (262144)`, i.e., the context window is intentionally small for latency, and very long input can overflow it). `service.py`'s `analyze_text()` catches this as a generic `Exception` (not `RuntimeBoundaryError`) and re-raises `RuntimeUnavailableError`, which `demo.py` maps to a `503` JSON error response — this is the *existing, frozen* `/api/analyze` contract behavior (`src/runtime/demo.py` lines 131-136), not new behavior.
- **Why this is not a UI bug:** The UI's job per the UIQ-01 acceptance bar (`31-UI-SPEC.md`) is to render "a rendered result bubble OR a well-formed error bubble" with zero orphaned typing nodes and a re-enabled button — and it does exactly that. The verifier's own `very_long` case record confirms: `response_status: 503`, `typing_count: 0`, `terminal_bubble_count: 1`, `button_disabled: false`, `new_page_error_count: 0`. The single captured console message (`"Failed to load resource: ... 503"`) is the browser's own standard network-log entry for a non-2xx fetch response, not an uncaught JS exception — `demo.js`'s `try { const response = await fetch(...) } ... if (!response.ok) { appendErrorBubble(...) }` path already handles this correctly and renders the server-supplied `payload.error.message`/`payload.error.steps` through the existing `error-template`.
- **Why no fix is applied:** Per this milestone's hard constraint ("Backend (synchronous wsgiref + POST /api/analyze) is frozen; no behavior changes") and this plan's explicit scope boundary ("do not modify `src/runtime/demo.py`, `src/runtime/service.py`, `/api/analyze` request/response shape... unless a prior decision is reopened"), fixing context-window overflow behavior (e.g., adding a client-side length guard, or a backend truncation/chunking strategy) would be an architectural change requiring its own decision, not a UIQ-04-scoped quirk fix. The current fail-closed behavior (surface a clear error rather than silently truncating or hallucinating on an overflowed context) is also consistent with the project's recall-first / fail-closed safety posture (STATE.md). **Decision: document only, no fix. Flagged as a candidate follow-up for a future milestone if very-long-message support becomes a requirement.**

## Finding 3: `double_submit` re-entrant controller ownership (UIQ-02/D-04)

- **Classification: app-origin — fixed in `demo.js`.**
- **Verifier evidence at time of triage:** Plan 31-01's live run already reported the `double_submit` case as `passed: true` (`completed_analyze_response_count: 1`, `completed_superseded_response_count: 0`, `abort_error_bubble_count: 0`, `typing_count: 0`, `button_disabled: false`). The verifier only inspects **final** DOM/telemetry state after both requests settle, so a pass here does not rule out a transient mid-flight race — it only proves the case's exact final-state assertions were not violated on this run.
- **Code-review finding (Pitfall 2, `31-RESEARCH.md`):** `analyzeMessage()`'s `finally` block unconditionally ran `setBusyState(false); currentController = null;` for *every* settling request, including one that had just been aborted by a newer request's `currentController.abort()` call. Because `AbortController.abort()` rejects the aborted request's `fetch()` promise as a microtask almost immediately (well before the newer request's real network round-trip completes), the aborted request's `finally` block runs first and briefly: (a) re-enables `#analyze-button` while the surviving request is still in flight, and (b) sets the shared `currentController` to `null` while the surviving request's `AbortController` is still the one that should own cancellation. A third rapid submission landing inside that window would not abort the still-in-flight second request (since `currentController` is `null`), and the second request's own later `finally` block would then redundantly clear state that a third request may have already taken ownership of. This exact scenario, and its exact fix, is spelled out in this plan's task action text and in `31-PATTERNS.md`'s "Abort/Re-entry Guard" section.
- **Fix applied:** `src/runtime/demo_assets/demo.js` — each call to `analyzeMessage()` now keeps a request-local `const controller = new AbortController()` (still assigned to the shared `currentController` for the *next* call's abort check), and the `finally` block only clears `currentController`/busy state when `currentController === controller`, i.e., only when this request is still the current one. An aborted/superseded request's `finally` now becomes a no-op for shared state (its own `typingEl.remove()` and `AbortError` swallowing still run as before, so no orphaned typing node or leaked error bubble is introduced).
- **Verification:** `.planning/phases/31-ui-quirks-edge-cases-regression-re-check/artifacts/31-ui-quirks-after-fix.json` (this plan's fresh live run, produced after the fix) and `tests/runtime/test_demo.py` (unchanged static/WSGI contract, still green) confirm no regression. No `data-slot`, template, CSS, or `/api/analyze` contract change was needed or made.
