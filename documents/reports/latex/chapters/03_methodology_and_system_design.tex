Each layer produces hash-bound artifacts or documented contracts that can be checked against the project files.

\section{Development Structure}
The implementation covers five empirical stages and one maintainability stage. The first produces the governed corpus and seed-group split lineage. The second measures ordinary LoRA and QLoRA on the target laptop before committing to the feasible adaptation route. The third completes local Qwen QLoRA and PhoBERT training and verifies the Qwen GGUF export. The fourth provides a text-only runtime with stable structured-output contracts. The fifth freezes both models and evaluates them once on the same 220-row terminal cohort. The final maintainability stage separates active application domains from historical experiment and evidence-production source; it does not alter or regenerate the frozen metrics.

\section{Data Construction and Split Governance}

The dataset was assembled from seed records collected by the retained \texttt{tinnhiemmang.vn} crawler and expanded into a controlled synthetic development corpus. After quality repair and lineage governance, the promoted corpus contains 2{,}097 rows across four classes: bank impersonation, Zalo social engineering, task scam, and benign. Each generated record first passes a Pydantic schema gate that checks types, required fields, permitted labels, score ranges, and evidence-span structure. A separate model-based judge assesses semantic quality (Section~\ref{sec:quality-check}), while targeted decisions are made by a Vietnamese-fluent reviewer. Pydantic is therefore used for structural validation, not as a semantic judge, and model judgments are not presented as human ground truth. The initial label is set at generation time. The generation scheduler creates repeated class-conditioned batches across its configured complex and bulk modes until each target is filled. At scoring time, the ground-truth label is withheld from model input and joined back only after prediction. \section{Offline Text Runtime Baseline}

The runtime is built around a stable text-only analysis interface. Messages are submitted as text, normalized locally, and dispatched to the configured backend. This design means that changing the backend does not affect the command-line interface or the output format. The backend returns a structured result that the rendering layer converts into a readable terminal report.

Privacy is treated as a first-class design requirement, consistent with the risk-management principles of the NIST Privacy Framework \cite{nist2026privacyframework}. In this implementation, raw message text does not leave the local device. The version~1 boundary is strictly text-only; OCR, image, audio, and mobile input channels are explicitly out of scope.

A readiness check verifies that the selected profile is loaded correctly before analysis begins. If the profile is not ready, the system stops with a diagnostic message instead of silently using an unintended configuration.

\section{Local Model Selection and Deployment Paths}

The selection pilot evaluated three open-weight candidates from the Qwen family \cite{qwen2025} on 33 fixed balanced examples under recall-first scoring: \texttt{qwen3-4b-instruct-2507}, \texttt{qwen3.5-4b}, and \texttt{qwen2.5-7b-instruct}. The evaluation used a three-tier outcome structure covering benign, suspicious, and high-risk inputs and was run locally on the target laptop hardware so that hardware fit was in scope from the start. All three candidates recorded 0.5000 overall risky-class recall in this small screen. The selected 4B candidate used approximately 2.8~GB peak VRAM and 0.35~seconds per sample, compared with 3.3~GB and 0.94~seconds for the other 4B candidate; the 7B candidate used approximately 5.6~GB. The selected 4B path therefore matched the observed recall with the best measured fit among the pilot candidates. Table~\ref{tab:pilot-comparison} shows the full screening results.

\input{tables/pilot_comparison}

\texttt{Qwen3-4B-Instruct-2507} was selected for the generative path because it met the pilot's recall and hardware-fit constraints and could emit the complete structured response. PhoBERT \cite{nguyen2020phobert} was added as a complementary Vietnamese encoder baseline rather than adapting a second Qwen candidate. This produced a more useful engineering comparison: a generative 4B model that returns label, evidence, and guidance versus a compact four-class classifier optimized for the label itself.

\label{sec:qwen-vs-phobert}
PhoBERT is a RoBERTa-style Vietnamese encoder trained with a masked-language-modeling objective. Its classification head is efficient for a closed label set but does not natively generate quoted evidence or recommendations. Qwen is a decoder and can generate those fields together in one JSON object. The two models therefore answer different deployment needs: PhoBERT supplies a strong and compact classification reference, while Qwen supplies the richer user-facing response. The evaluation compares their common four-class output only; it does not imply that PhoBERT produces Qwen's explanatory fields.

\subsection{Measured LoRA--QLoRA Decision}
The adaptation choice was made from bounded same-machine evidence. An ordinary full-precision LoRA probe retained 31 optimizer-step events, including 26 measured steps. Its median measured step took 53.274~seconds, giving an incomplete-window compute extrapolation of 18.42--18.88~hours for 1{,}245 steps before evaluation and checkpoint overhead. Device-memory use peaked at 7{,}902 of 8{,}151~MiB, with a minimum of 9~MiB free. The run ended with a controller error before its target window; it did not record a CUDA or system out-of-memory exception. The correct conclusion is therefore that ordinary LoRA was technically runnable but operationally unattractive under the deadline and available memory headroom, not that LoRA was impossible.

A separately dated genuine QLoRA probe activated NF4 with double quantization, verified 252 four-bit linear modules, froze the base model, and retained exactly five warm-up plus 40 measured steps. Median step time was 3.462389~seconds, corresponding to a 72-minute-49.750-second optimizer-plus-one-validation/save projection under the bounded probe assumptions. Peak device-memory use was 7{,}516/8{,}151~MiB, and no OOM or thermal stop was recorded. Because the projection excludes the full cadence of checkpoint generation and validation, it is used only as feasibility evidence. These measurements motivated the completed QLoRA route without converting a resource comparison into an accuracy claim.

\subsection{Completed Qwen QLoRA and PhoBERT Training}
The fresh Qwen run used the promoted 1{,}658-row training and 219-row validation identities, genuine NF4 QLoRA \cite{dettmers2023qlora}, and a deterministic structured-output parser. It completed 1{,}245 optimizer steps from step zero. The selected step-200 checkpoint recorded validation macro F1 0.988515 and accuracy 0.990868, zero invalid outputs, and passed the declared safety gates. These are development-validation measurements used for checkpoint selection, not the terminal model comparison.

Each Pydantic-validated dataset record is converted into an instruction and a JSON response containing the class label, risk tier, suspicious spans, and explanation. The two parts are serialized under \texttt{Instruction} and \texttt{Response} headings, tokenized to a maximum sequence length of 1{,}024, and used with a causal language-model objective over the serialized sequence. During evaluation, the generated class value is decoded to one of the four labels for the confusion matrix. The user-facing runtime can subsequently present one or more threat labels after applying its structured decision contract; this runtime presentation is distinct from the single-label experimental metric.

This is a deliberate architectural choice and not the only way to reach a classification decision from a fine-tuned LLM. An alternative, also used in practice, is to attach a small classification head to the decoder's final hidden state and train that head directly, leaving text generation out of the loop entirely \cite{yousefiramandi2025finetuning}. That head-based route can reach a well-calibrated single label with fewer trainable parameters. It has no native mechanism, however, for the other two fields this system also has to produce: an evidence span copied from the input text and a short recommendation. Adding those would mean training a second, separate generation component alongside the head, with the two outputs reconciled after the fact rather than produced together. This project instead trains the decoder to emit the label as part of one generated JSON object, alongside the evidence and recommendation fields, in a single forward pass. The class label functions as a \textit{verbalizer} \cite{schick2021pet}: a fixed, closed vocabulary of literal strings (\texttt{bank\_impersonation}, \texttt{zalo\_social\_engineering}, \texttt{task\_scam}, \texttt{benign}) that the fine-tuned model is trained to reproduce, following the classification-as-generation framing introduced with T5 \cite{raffel2020t5}. QLoRA itself adds no classification-specific layers; it adapts the existing attention and projection weights, and the classification signal comes entirely from the next-token training objective applied to the label field. Narang et al.\ report that generating a label and its explanation together, in one pass, produces a more consistent label--explanation relationship than predicting the label first and explaining it afterward with a separate mechanism \cite{narang2020wt5}, which is the same reasoning behind generating the label, the evidence spans, and the recommendation together here. A classification head remains the better choice when a single label is the only required output; this project needed the other two fields as well, produced from the same generation context as the label rather than reconciled after the fact.

The adapted forward pass combines the frozen pretrained weight matrix~$W_0$ with the low-rank product~$BA$, scaled by~$\alpha/r$:
\begin{equation}
  h = W_0\, x + \frac{\alpha}{r}\, B A\, x
  \label{eq:qlora-forward}
\end{equation}
where $B \in \mathbb{R}^{d \times r}$, $A \in \mathbb{R}^{r \times k}$, and $r \ll \min(d, k)$.

\noindent\textbf{Qwen training procedure:} only the low-rank matrices $A$ and $B$ in Equation~\ref{eq:qlora-forward} were updated; the base weights $W_0$ remained frozen in 4-bit NF4. Each micro-batch contained one serialized instruction--response pair, and four micro-batches were accumulated for each optimizer update (effective batch size 4). The standard causal language-modeling cross-entropy covered the complete response, including the literal class label. A wrong label therefore contributed directly to the token loss. Validation predictions, checkpoint selection, raw events, resolved configuration, hardware identity, and graph inputs were retained and hash-verified. \subsection{Terminal Shared-Cohort Evaluation}
Both frozen models were invoked in one terminal evaluation over the same 220-row cohort. Qwen QLoRA achieved accuracy 0.981818, macro F1 0.980493, and weighted F1 0.981848. PhoBERT achieved accuracy 0.990909, macro F1 0.990892, and weighted F1 0.990925. Each produced zero invalid outputs and one risky-to-benign error. PhoBERT was higher on the recorded aggregate metrics, while Qwen was higher on benign precision, recall, and F1. These are descriptive results from one cohort and do not establish statistical significance or stable superiority.

The run created its durable claim before model access and was not retried. Five earlier launch attempts failed before that claim and before terminal row access; their failures were preserved as infrastructure evidence rather than erased. A later provenance audit established that broad automated integrity tests had parsed, statted, and hashed the split files before the terminal model evaluation, and one focused regression reread them afterward. Those reads displayed no row content to a human, called no model or external service, and did not affect training, selection, thresholds, repair, inference, or retry. Accordingly, the result is one terminal two-model evaluation, but the split is not described as having zero prior filesystem access.

\section{Explainable Threat Decisioning}

The decision layer returns four elements for each message: a risk tier (benign, suspicious, or high-risk), one or more in-scope threat labels for risky inputs, grounded suspicious cues taken from spans of the analyzed text, and safe next-step recommendations. This structure follows the principle that explainability should be grounded in observable evidence rather than in opaque model confidence scores alone \cite{rjoub2023surveyxai}.

The decision layer follows two design rules. Cues must be drawn from the message text itself rather than inferred from model confidence scores alone. Recommendations must stay within a safe, generic set and must not instruct users to take actions that could cause harm. Together these rules help keep the output useful and grounded rather than misleading.

The generative-classification design in Section~\ref{sec:qwen-vs-phobert} raises a practical question a fixed-size classification head does not have: a decoder generates free-form text, so the raw output is not guaranteed to be a single, well-formed JSON object even when the model is well-trained. The runtime does not assume clean output. It scans the raw generation for every candidate JSON object (every position where an opening brace could start one), decodes each candidate independently, and applies the implemented weighted heuristic over recognized field aliases and nested-structure penalties, keeping the best-scoring match. If no candidate parses as a JSON object at all, the analyzer raises an explicit error rather than guessing a label or silently defaulting to benign. This is the same fail-closed principle applied at the model-output boundary that the profile-readiness check below applies at the deployment boundary.

A parsed payload is not automatically trusted either. The decision object is validated against four cross-field consistency rules before it can reach the user: \texttt{benign} cannot appear alongside another threat label in the same decision; a \texttt{benign} risk tier must map to exactly the \texttt{benign} label and nothing else; a non-\texttt{benign} tier must not include the \texttt{benign} label; and a \texttt{high-risk} tier must be backed by at least one evidence item, not an empty list. A decision that violates any of these rules is rejected before rendering, rather than displayed as-is. These rules exist because a decoder that generates a full JSON object one token at a time can produce an internally inconsistent object --- for example, a high-confidence-sounding summary paired with an empty evidence list --- in a way a fixed-size classification head, which only ever emits one label field, structurally cannot.

A safety rule applies at the runtime boundary: if the configured profile is not ready, the system stops and reports the reason instead of silently switching to a fallback. This applies to both the laptop GGUF profile and the accelerated local profile.

\section{Maintainability and Provenance Separation}

The maintained application is organized around named runtime, integrity/artifact, data, modeling, and evidence domains. The installed \texttt{vnphish} entry point exposes \texttt{analyze}, \texttt{doctor}, and \texttt{demo}; older model-adaptation commands and data paths are retained behind explicit compatibility adapters. Historical experiment implementations remain available for provenance, but they are not presented as the forward-facing domain model.

This separation is important for scientific traceability. The frozen metrics above belong to the hash-identified historical producer source and verified result export, accompanied by the mandatory provenance correction. The refactored worktree did not generate, recompute, or improve those metrics. An adversarial review of the reorganized architecture passed its bounded 128-test gate but still reported six critical and three warning findings, including guard-boundary, route-discovery, local-demo, and terminal-rendering issues. These findings are retained as open hardening work rather than hidden behind a claim that the architecture or security review is fully closed.

\section{Design Principles}

Three design principles run through the whole system. First, later layers do not relax the local-first privacy posture established at the runtime boundary. Second, data admission is governed by semantic lineage as well as record-level quality, so paraphrases cannot manufacture independent seeds. Third, claims are tied to stable contracts, manifests, and explicit limitations: failed attempts, incomplete probes, prior-access corrections, and unresolved review findings remain part of the evidence rather than being rewritten as success.
