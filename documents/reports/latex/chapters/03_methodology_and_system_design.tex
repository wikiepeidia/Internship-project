\section{Development Structure}
The implementation covers four main stages, followed by a final evaluation. The first stage produces the dataset and split lineage. The second provides a text-only local runtime with stable input and output contracts. The third selects and deploys a local model family under hardware limits. The fourth adds structured risk reasoning and explanation output. The final stage evaluates the full stack on the internal validation split and records the project result.

\section{Data Construction and Split Governance}

The dataset was assembled from seed records collected on \textit{tinnhiemmang.vn}, a public Vietnamese cybercrime alert portal, and expanded into a synthetic development corpus using the \texttt{claude-3-5-haiku} API. The final corpus contains 3{,}000 rows across four classes: bank impersonation, Zalo social engineering, task scam, and benign. Each generated record first passes a Pydantic schema gate that checks types, required fields, permitted labels, score ranges, and evidence-span structure. A separate LLM-based judge then assesses a sample for realism and label correctness (Section~\ref{sec:quality-check}). Pydantic is therefore used for structural validation, not as a semantic quality judge. Two representative examples are shown below.

\noindent This corpus supports model development and internal validation; it is not presented as a substitute for a real-world, human-labeled benchmark. Each build is tied to versioned manifests with SHA-256 content hashes so that evaluation results can be traced to the exact dataset snapshot used.

\label{sec:quality-check}
An LLM-based quality-judge pass reviewed 100 generated examples in two batches of 50 (the first scored by \texttt{claude-3-5-haiku}, the second by \texttt{Qwen2.5-7B-Instruct} to reduce single-judge bias). Ninety-four passed inspection. The combined average realism score was 4.43 out of 5 ($t = 8.7$, $p < 0.0001$, one-sample $t$-test against $H_0\colon \mu \leq 4.0$) and the average label-correctness score was 4.92 out of 5 ($t = 53.2$, $p < 0.0001$). Both scores reject the null hypothesis at $\alpha = 0.001$. This automated review reduces the risk of low-quality rows entering the training split but is not a substitute for independent human annotation.

The dataset split contains 2{,}333 training examples, 254 validation examples, and 413 test examples, totaling 3{,}000 records. The reported evaluation uses the 254-row validation split. A documented limitation of the current generation pipeline is that one seed group appears across multiple splits; the metrics should therefore be read as internal development evidence rather than independent test performance. The 413-row test split remains reserved for future benchmarking on an independent evaluation. Table~\ref{tab:dataset-stats} summarizes the split sizes and validation support.

\section{Offline Text Runtime Baseline}

The runtime is built around a stable text-only analysis interface. Messages are submitted as text, normalized locally, and dispatched to the configured backend. This design means that changing the backend does not affect the command-line interface or the output format. The backend returns a structured result that the rendering layer converts into a readable terminal report.

Privacy is treated as a first-class design requirement, consistent with the risk-management principles of the NIST Privacy Framework \cite{nist2026privacyframework}. In this implementation, raw message text does not leave the local device. The version~1 boundary is strictly text-only; OCR, image, audio, and mobile input channels are explicitly out of scope.

A readiness check verifies that the selected profile is loaded correctly before analysis begins. If the profile is not ready, the system stops with a diagnostic message instead of silently using an unintended configuration.

\section{Local Model Selection and Deployment Paths}

The selection pilot evaluated three open-weight candidates from the Qwen family \cite{qwen2025} on 33 fixed balanced examples under recall-first scoring: \texttt{qwen3-4b-instruct-2507}, \texttt{qwen3.5-4b}, and \texttt{qwen2.5-7b-instruct}. The evaluation used a three-tier outcome structure covering benign, suspicious, and high-risk inputs and was run locally on the target laptop hardware so that hardware-fit was in scope from the start. Both 4B candidates correctly identified all 11 high-risk examples before fine-tuning, while the 7B model missed all 11 despite performing adequately on the suspicious tier. The 7B model also required approximately 5.6~GB of peak memory compared to 2.8~GB for the selected 4B candidate. Hardware fit and recall performance together made the 4B path the delivery target. Table~\ref{tab:pilot-comparison} shows the full screening results.

\input{tables/pilot_comparison}

\texttt{qwen3-4b-instruct-2507} was selected as the deployed model and \texttt{qwen3.5-4b} as the alternative candidate on the basis of recall performance and hardware fit. Both paths were taken through the full adaptation workflow. The selection notes from the pilot manifest record the basis explicitly: recall-first weighted scoring under the laptop constraint was the deciding criterion.

The pilot compared only decoder-only candidates from the Qwen family; it did not include PhoBERT \cite{nguyen2020phobert}, the Vietnamese-specialized encoder already referenced in Table~\ref{tab:approach-comparison}. That comparison is stated explicitly here rather than left implicit. PhoBERT is a RoBERTa-style Transformer encoder trained with a masked-language-modeling objective; it has no decoder and no generative capability. Its standard use pattern attaches a classification head to its pooled representation and would plausibly perform this project's four-class labeling step well, at lower computational cost than a 4-billion-parameter decoder. It cannot, however, produce free-form text, so it has no native path to the evidence-span quoting or safe-action recommendation text this system also returns; the Vietnamese NLP group that built PhoBERT released a separate encoder-decoder model, BARTpho \cite{tran2021bartpho}, specifically because generation was a different problem. Producing all three outputs --- label, grounded evidence, and recommendation --- from a PhoBERT-based pipeline would require coupling the encoder to a second, separately trained generation component, with no architectural guarantee that the two stay consistent with each other. \texttt{Qwen3-4B-Instruct-2507} produces all three from a single fine-tuned decoder in one forward pass, which is why it was adapted for this task rather than an encoder-only alternative. Qwen's much larger multilingual pretraining base (Vietnamese and English together, among other languages \cite{qwen2025}) also leaves room to extend the same adapter to English-language scam text later, whereas PhoBERT's pretraining corpus and tokenizer are Vietnamese-only; this is a secondary consideration, not the reason for the initial choice, which rests on the output shape required, not on language coverage. The trade-off is acknowledged rather than hidden: for a system that only needed to emit a single label, PhoBERT would be the smaller, cheaper, well-precedented choice.

The selected model (\texttt{Qwen3-4B-Instruct-2507}) was adapted using QLoRA \cite{dettmers2023qlora} with rank $r{=}16$, scale $\alpha{=}32$, and 4-bit NF4 quantization with double quantization enabled. The recorded training job used 2{,}333 training examples and 254 validation examples for one epoch. It saved checkpoint 584 and reached a training loss of 0.5073. These values are read directly from the adapter's \texttt{training-summary.json}. Table~\ref{tab:qlora-config} summarises the configuration. Wall-clock training time is not used for hardware comparison because it depends on the accelerator and software environment.

Each Pydantic-validated dataset record is converted into an instruction and a JSON response containing the class label, risk tier, suspicious spans, and explanation. The two parts are serialized under \texttt{Instruction} and \texttt{Response} headings, tokenized to a maximum sequence length of 1{,}024, and used with a causal language-model objective over the serialized sequence. During evaluation, the generated class value is decoded to one of the four labels for the confusion matrix. The user-facing runtime can subsequently present one or more threat labels after applying its structured decision contract; this runtime presentation is distinct from the single-label experimental metric.

This is a deliberate architectural choice and not the only way to reach a classification decision from a fine-tuned LLM. An alternative, also used in practice, is to attach a small classification head to the decoder's final hidden state and train that head directly, leaving text generation out of the loop entirely \cite{yousefiramandi2025finetuning}. That head-based route can reach a well-calibrated single label with fewer trainable parameters. It has no native mechanism, however, for the other two fields this system also has to produce: an evidence span copied from the input text and a short recommendation. Adding those would mean training a second, separate generation component alongside the head, with the two outputs reconciled after the fact rather than produced together. This project instead trains the decoder to emit the label as part of one generated JSON object, alongside the evidence and recommendation fields, in a single forward pass. The class label functions as a \textit{verbalizer} \cite{schick2021pet}: a fixed, closed vocabulary of literal strings (\texttt{bank\_impersonation}, \texttt{zalo\_social\_engineering}, \texttt{task\_scam}, \texttt{benign}) that the fine-tuned model is trained to reproduce, following the classification-as-generation framing introduced with T5 \cite{raffel2020t5}. QLoRA itself adds no classification-specific layers; it adapts the existing attention and projection weights, and the classification signal comes entirely from the next-token training objective applied to the label field. Narang et al.\ report that generating a label and its explanation together, in one pass, produces a more consistent label--explanation relationship than predicting the label first and explaining it afterward with a separate mechanism \cite{narang2020wt5}, which is the same reasoning behind generating the label, the evidence spans, and the recommendation together here. A classification head remains the better choice when a single label is the only required output; this project needed the other two fields as well, produced from the same generation context as the label rather than reconciled after the fact.

The adapted forward pass combines the frozen pretrained weight matrix~$W_0$ with the low-rank product~$BA$, scaled by~$\alpha/r$:
\begin{equation}
  h = W_0\, x + \frac{\alpha}{r}\, B A\, x
  \label{eq:qlora-forward}
\end{equation}
where $B \in \mathbb{R}^{d \times r}$, $A \in \mathbb{R}^{r \times k}$, and $r \ll \min(d, k)$.

After training, the QLoRA adapter was merged back into the base weights and the merged model was exported to GGUF format with \texttt{q8\_0} quantization using the \texttt{convert\_hf\_to\_gguf.py} script. Inference uses \texttt{llama.cpp} \cite{gerganov2023llamacpp} as the CPU runtime backend. The two quantization schemes serve different purposes: NF4 4-bit reduces memory use during QLoRA fine-tuning, whereas Q8\_0 8-bit is used for the GGUF inference artifact. The exported artifact enables local CPU inference without CUDA at runtime. In a single-message verification on the target laptop (Intel Core i5, 16\,GB RAM, no discrete GPU), one message completed in approximately 24~seconds. This single observation meets the 30-second prototype target but is not a throughput benchmark.

\section{Explainable Threat Decisioning}

The decision layer returns four elements for each message: a risk tier (benign, suspicious, or high-risk), one or more in-scope threat labels for risky inputs, grounded suspicious cues taken from spans of the analyzed text, and safe next-step recommendations. This structure follows the principle that explainability should be grounded in observable evidence rather than in opaque model confidence scores alone \cite{rjoub2023surveyxai}.

The decision layer follows two design rules. Cues must be drawn from the message text itself rather than inferred from model confidence scores alone. Recommendations must stay within a safe, generic set and must not instruct users to take actions that could cause harm. Together these rules help keep the output useful and grounded rather than misleading.

A safety rule applies at the runtime boundary: if the configured profile is not ready, the system stops and reports the reason instead of silently switching to a fallback. This applies to both the laptop GGUF profile and the accelerated local profile.

\section{Design Principles}

Two design principles run through the whole system. First, later layers do not relax the local-first privacy posture established at the runtime boundary. Second, later layers reuse stable contracts and manifests created earlier in the stack, which makes the system easier to validate, reproduce, and explain.
