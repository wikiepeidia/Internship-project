This chapter maps the implemented system to the actual codebase organization. The codebase is split into three main subsystems: the data pipeline under \texttt{src/data\_pipeline}, the user-facing runtime under \texttt{src/runtime}, and the local adaptation workflow under \texttt{src/model\_adaptation}. This separation shows that the system works as one connected pipeline rather than a collection of isolated scripts.

\section{Codebase Organization}

The structural layout of the source repository is organized as follows:

\begin{quote}
\begin{verbatim}
src/
├── data_pipeline/           # Subsystem (1): Data Construction
│   ├── cli.py               # Dataset engineering CLI
│   └── schemas.py           # Pydantic data provenance models
├── runtime/                 # Subsystem (2): User Runtime
│   ├── cli.py               # vnphish demo & doctor entry points
│   ├── contracts.py         # AnalysisRequest & AnalysisResult
│   ├── service.py           # Normalization & backend dispatch
│   └── render.py            # Terminal output formatting
└── model_adaptation/        # Subsystem (3): Model Training
    ├── catalog.py           # Qwen candidate registry
    └── training.py          # QLoRA fine-tuning orchestration
\end{verbatim}
\end{quote}

The three main packages divide responsibility cleanly. The data-pipeline package handles schemas, scraping, normalization, synthetic generation, quality judging, and versioned manifest output. The runtime package exposes the public analysis contract, the service boundary, backend dispatchers, rendering, and the doctor readiness checker. The model-adaptation package manages candidate catalogs, pilot scoring, training orchestration, GGUF conversion, and the off-device registry integration. This division was chosen so that each package can be read and tested independently even though the three packages form one connected system at runtime.

The main command-line entry point is \texttt{vnphish}, registered as a console script in \texttt{pyproject.toml}. The primary demo launch paths are \texttt{vnphish demo} and \texttt{python -m src.runtime.cli demo}. The readiness check is available as \texttt{vnphish doctor} or \texttt{python -m src.runtime.cli doctor}. All entry points are documented in the user guide shipped with the codebase.

\section{Data Pipeline Implementation}

The data-pipeline implementation centers on typed schemas and a single command-line interface. Seed records, dataset records, and manifest entries are validated through Pydantic models so that each stage operates on a known data shape and shape violations are caught at ingestion rather than at analysis time. This makes debugging pipeline failures cheaper because errors surface at the boundary where they originate rather than inside downstream training or runtime code.

The synthetic generation and quality-judge steps are explicit CLI commands rather than embedded notebook cells. This keeps provenance visible: each generation batch records the source seed file, the target count, the provider, and the version tag, and each quality-judge run records pass counts and score averages before the batch merges into the corpus. Keeping these steps separate reduces accidental contamination between build stages and makes it possible to re-run only the judging step if generation succeeds but scores are low.

Versioned manifests record the SHA-256 content hash, build timestamp, and git commit identifier for each produced artifact. This means a later evaluation claim can name the specific manifest version it relied on rather than restating the corpus description from memory.

\section{Runtime Contracts and Service Boundary}

The runtime is built around explicit interfaces. \texttt{AnalysisRequest} and \texttt{AnalysisResult} are the primary public types. Both are defined in the runtime contracts module and are the only types that cross the service boundary. This keeps the command-line interface stable even when the backend changes: callers construct an \texttt{AnalysisRequest}, pass it to the service layer, and receive an \texttt{AnalysisResult} regardless of which backend is active.

The service layer performs message normalization and dispatches to the configured backend \cite{nist2026privacyframework}. The renderer converts the structured result into a readable terminal report. This separation means that changing the display format requires no changes to the analysis contract, and adding a new backend requires no changes to the renderer.

The readiness check uses the same service boundary. Before analysis begins, it reports the selected backend and profile and checks whether the expected model artifacts are present. If they are not, the system stops rather than proceeding with an unintended backend.

\section{Backend Implementations}

Two local model backends are available in the shipped codebase. The \texttt{gguf-laptop} profile targets CPU inference via \texttt{llama.cpp} using the \texttt{Qwen3.5-4B} GGUF Q8\_0 artifact. This is the default local profile and the path validated on the project laptop hardware. The \texttt{accelerated-local} profile targets stronger GPU hardware and reuses the same \texttt{AnalysisResult} contract, so the rendering layer does not need to branch on backend type.

The heuristic backend provides the offline baseline when no model artifact is available. All three backends return the same \texttt{AnalysisResult} type, which means the command-line interface remains consistent across backend families. Profile selection is explicit: the user sets the profile in a settings file before startup rather than relying on auto-detection. A readiness check verifies the selected profile before any analysis begins. If the selected profile is not ready, the system reports the reason and stops rather than silently falling back to a different configuration.

\section{Model Adaptation Workflow}

The adaptation package coordinates three steps: candidate selection via a pilot scorecard, training via the QLoRA workflow, and artifact registration in the off-device model registry. The candidate catalog locks the set of Qwen model checkpoints considered for the project and records the selection result alongside the pilot scoring data. This means the selection decision is tied to a named artifact rather than left as an informal record.

Training scripts run over the retained dataset and save periodic checkpoints. After training completes, the convert command merges the adapter weights and exports a GGUF artifact at \texttt{q8\_0} quantization. The export uses \texttt{convert\_hf\_to\_gguf.py} with direct \texttt{q8\_0} output to produce a single artifact that supports CPU inference without a separate quantization step. The exported artifact is then registered in the off-device model registry.

Registry-based artifact resolution ensures the runtime always loads the newest registered adapter and GGUF file. This prevents stale artifacts from being selected after a new training or conversion run, which would otherwise be a silent correctness hazard if the registry were not updated consistently.

\section{Operator Surface and Packaging}

The \texttt{pyproject.toml} separates dependencies into three groups: \texttt{dev} for development and testing tools, \texttt{train} for GPU-dependent training libraries, and \texttt{runtime} for the inference-only deployment path. A user who only wants to run the analysis demo can install only the \texttt{runtime} group without pulling in training dependencies such as PEFT or the CUDA-aware transformer libraries. This separation was important for the thesis demonstration because the laptop environment needed a clean inference-only install path that did not require the full training stack.

The demo server is started with \texttt{vnphish demo} or \texttt{python -m src.runtime.cli demo}. It loads the configured GGUF model \cite{gerganov2023llamacpp} once at startup so that the first analysis request after the browser opens does not face the full cold-load time. The target warm latency on the laptop CPU is approximately 13~seconds after the prompt-size optimization pass. The demo opens a local browser page where the user can paste a suspicious message, choose an optional channel hint, and review the risk tier, threat labels, grounded suspicious cues, and safe next steps without using CLI syntax.

\subsection{Example Analysis Output}

The following examples show the output produced by running \texttt{vnphish analyze} through the same runtime contract used by the local demo. The first case is a common bank-impersonation message, while the second and third cases show a brief qualitative check on a noisy scam-style SMS and a benign OTP notification.

\textbf{Threat Labels:} Bank impersonation, Task scam

\medskip
\textbf{Grounded Cues:}
\begin{itemize}[leftmargin=1.5em, topsep=2pt, itemsep=1pt]
  \item \textit{``mã OTP''} --- Yêu cầu mã xác thực hoặc thông tin đăng nhập nhạy cảm.
  \item \textit{``mở khóa''} --- Dẫn người dùng tới thao tác xác minh hoặc liên kết đăng nhập.
\end{itemize}

\textbf{Next Steps:}
\begin{itemize}[leftmargin=1.5em, topsep=2pt, itemsep=1pt]
  \item Không gửi OTP cho bất kỳ ai qua Zalo hay tin nhắn.
  \item Liên hệ trực tiếp Vietcombank qua số hotline chính thức 1900\,54\,54\,26.
  \item Kiểm tra lại giao dịch trên ứng dụng ngân hàng của bạn trước khi hành động.
\end{itemize}
\end{quote}

The system returned two threat labels for this message --- bank impersonation and task scam --- reflecting the overlapping linguistic signals discussed in Section~IV. The grounded cues are drawn directly from spans of the input text, and the next-step recommendations reference the specific institution named in the message, showing that the output is contextualised rather than generic.
