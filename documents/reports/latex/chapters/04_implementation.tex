This chapter covers what was actually built and run: the installed application, how the dataset was produced in practice, the two training runs, the exported model, and the things that went wrong along the way. The design reasoning behind these choices is in Chapter~III; the results they produced are in Chapter~V.

\section{The Installed Application}

To make the trained model convenient to run, it is wired into an executable application called \texttt{vnphish}. It has three commands, and the one that matters is:

\begin{quote}
\texttt{vnphish analyze --text "<message>"}
\end{quote}

\noindent This takes one Vietnamese message and prints the result. The other two are support commands: \texttt{vnphish doctor} checks that the model and settings loaded correctly before anything is analysed, and \texttt{vnphish demo} opens the same analysis in a local browser page for demonstration.

The source tree is organised by what each part does:

\begin{quote}
\begin{verbatim}
src/
  core/             strict JSON validation and safe file writes
  artifacts/        reading model and result files
  config/           local settings
  data_pipeline/    building the dataset: records, text handling,
                    splitting, generation, judging, one-off repairs
  modeling/         training, inference and evaluation
  runtime/          the CLI, the analysis service, the demo page
  source_archiving/ keeping a fixed copy of the source
  model_adaptation/ the older experiment code, kept for reference
\end{verbatim}
\end{quote}

\section{Building the Dataset}

Every message carries the \texttt{seed\_id} of the article it was written from, and the splitter sends all messages sharing an ID into one split. That rule is stricter than splitting message by message, and it is what stops a reworded message from appearing on both sides of the evaluation.

The first pass was generated by Claude 3.5 Haiku, one class at a time. Reviewing it showed that a large part was not usable. One whole group of Zalo messages had been written as third-person narration, describing a scam rather than being one. Other classes carried leftover template text: bracketed placeholders such as \texttt{[CCCDUpdateApp]}, unresolved URLs such as \texttt{[http://xyz-bank-update.com]}, and obviously fake domains such as \texttt{fake-bank.vn}.

The narration problem is easiest to see in an example. This message was in the set, labelled as a Zalo scam:

\begin{quote}\small\itshape
``Tin nhắn thoại trên Zalo được chép lại: `Con trai của người nhận vừa được đưa vào khoa cấp cứu. Người gửi nói cuộc gọi video chỉ hiện khuôn mặt vài giây rồi mất tiếng. Bệnh viện cần tạm ứng trước khi phẫu thuật.'\,''
\end{quote}

\noindent It reads as a report \emph{about} a scam. The victim is ``the recipient'', the scammer is ``the sender'', and the whole thing is introduced as a transcript. No real message is written that way, and a model trained on it learns to recognise scam summaries rather than scams. The judge scored its realism 2 out of 5, and the reviewer marked it FAIL.

Those messages were rewritten rather than patched, and it is worth being exact about what that means, because it is not hand-editing. Nobody swapped \texttt{fake-bank.vn} for a different invented bank. What was kept from each affected message was its \textit{scenario root}: the relationship being faked, the pretext, the action requested, and the harm that follows. From that root a new message was written in the first person, as the scammer would actually send it. The replacement for the message above, built from the same source article, reads:

\begin{quote}\small\itshape
``Tôi vừa trao đổi nhanh qua video về tình trạng của cháu nhưng đường truyền trong viện bị ngắt. Ca này không thể chờ lâu; anh/chị quét mã QR này để chuyển khoản viện phí và gửi xác nhận cho tôi ngay.''
\end{quote}

\noindent Same scenario, same source article, same seed identifier, so the message stays in whichever split its article was already assigned to. The wording itself was produced by a language model in a separate session, then stored in the project as fixed text and applied offline, so the repair made no external API call. Every replacement then went through the same automatic checks as everything else.

A judge model scored every message, and a Vietnamese-speaking reviewer checked a sample by hand and worked through the messages whose labels looked wrong. What the checks found is reported in Chapter~V.

\section{Measuring LoRA Against QLoRA}

Both training methods were run briefly on the target laptop before either was committed to. These were short measurement runs, not attempts to train a usable model, and the adapters they produced were deleted afterwards.

\subsection{Ordinary LoRA}

The LoRA run recorded 31 optimizer steps, 26 of them measured. It ran for 1{,}782.206~seconds, just under thirty minutes, with a median step of 53.274~seconds. Multiplying that median across the planned 1{,}245-step schedule gives roughly 18.42~hours of computation, and the mean-step version gives 18.88~hours. Neither figure includes the time spent on validation and saving checkpoints, so neither is a prediction of how long the run would actually take.

Memory was the deciding factor. The card holds 8{,}151~MiB, and at its tightest moment \texttt{nvidia-smi} reported only 9~MiB of it still free.

The run did real optimizer work with sensible losses and produced no out-of-memory error; it stopped early for an unrelated driver fault. The problem is the combination: an eighteen-hour run with almost no memory to spare is a bad bet, because any brief extra allocation would end it and cost most of a day.

\subsection{NF4 QLoRA}

The QLoRA run confirmed that 4-bit NF4 was genuinely active: 252 four-bit layers, a frozen base model, and 504 trainable adapter tensors. It completed five warm-up steps plus 40 measured ones, with a median step of 3.462389~seconds across the 40 measured. The progress bar in Figure~\ref{fig:probe-console} reports 3.70~s/it, which is its own running average over all 45 steps including the slower warm-up; the two numbers describe the same run.

Memory peaked at 7{,}516 of 8{,}151~MiB, leaving a workable margin throughout, and no out-of-memory error or thermal stop occurred. Figure~\ref{fig:resource-probe-comparison} compares the two runs, and Figure~\ref{fig:probe-console} is the console output as it appeared while this one was running.

\section{Training Qwen}

The full Qwen run used the 1{,}658 training and 219 validation messages, three epochs, and 1{,}245 optimizer steps from a fresh start. The package versions were Python~3.13.13, PyTorch~2.12.0+cu132, Transformers~5.9.0, PEFT~0.19.1, and bitsandbytes~0.50.1.

The model was evaluated every 50 steps, and the checkpoint that scored best on the validation messages was kept. That turned out to be step 200. Later checkpoints trained longer but did not score better, which is what the evaluation sweep in Figure~\ref{fig:checkpoint-sweep} shows. \subsection*{Qwen's Answer on Three Messages}
\label{sec:worked-example}

Three messages were put through the installed application afterwards: a bank-impersonation
scam, a genuine transaction notice, and a genuine one-time-password notice. The
first two come out right. The third does not, and it is reported here because it
shows the shape of the system's weakness better than the first two show its
strength.

\subsubsection*{Input 1: A Scam Message}

Typed without diacritics, in the way a real SMS often is.

\begin{quote}\small\itshape
``{[}VIETCOMBANK{]} Tai khoan cua ban vua bi truy cap tu thiet bi la luc 03:47 SA. Neu ko phai ban, bam vao link de khoa ngay: \textup{\texttt{http://vcb-secure-alert.net/lock?id=9182736}} hoac goi 1800.9999 (mien phi).''
\end{quote}

\noindent The system returned \texttt{high-risk} with the label
\texttt{bank\_impersonation}, which is correct. It quoted three cues: the link,
the claim that the account was accessed at 03:47, and the free-phone number. Its
advice was:

\begin{quote}\small\itshape
``Không truy cập link hoặc gọi số điện thoại trong tin nhắn này.''\\
``Kiểm tra lại thông tin đăng nhập trên thiết bị của bạn.''\\
``Liên hệ trực tiếp với Vietcombank qua số hotline chính thức để xác minh.''
\end{quote}

\noindent This is what the project is for. The label alone would tell the user
little; the quoted phrases show which part of the message caused the warning, and
each suggestion sends the user to a channel they choose themselves. None tells
them to tap the link, reply, or read out a code, which is the rule the runtime
applies to this field before anything is displayed.

\subsubsection*{Input 2: A Genuine Transaction Notice}

A real payment confirmation, also without diacritics.

\begin{quote}\small\itshape
``VCB: TK 0123456789 -250,000 VND luc 09:15 12/09. Noi dung: THANH TOAN HOA DON DIEN EVN HANOI. So du: 8,420,000 VND.''
\end{quote}

\noindent The system returned \texttt{benign}, which is correct. It quoted the
debit line, the payment description, and the closing balance, and its advice was
ordinary and harmless: check the electricity bill, contact EVN if anything looks
wrong, and share neither account details nor an OTP with anyone. The message
mentions a bank, an account number and an amount, and the system still does not
flag it.

\subsubsection*{Input 3: A Genuine Notice Misclassified}
\label{sec:false-alarm}

A real Smart OTP message, which even warns the reader not to share the code.

\begin{quote}\small\itshape
``VPBank Smart OTP: Mã xác thực của bạn là 847291. Mã này có hiệu lực trong 90 giây để xác nhận đăng nhập Internet Banking. Tuyệt đối KHÔNG chia sẻ mã này với bất kỳ ai, kể cả nhân viên ngân hàng.''
\end{quote}

\noindent Here the system was wrong. It returned \texttt{suspicious} rather than
benign. The label it attached was \texttt{bank\_\hspace{0pt}impersonation}, and the cues it
quoted were ``Smart OTP'', ``đăng nhập'', and ``Internet Banking''. Its advice
was to check the official VPBank app, share the code with nobody, and call the
bank directly.

\subsubsection*{Interpretation of the Third Result}

Six ordinary bank messages were tried in total: transaction confirmations, a
balance notice, a maintenance notice, a statement notice, and the OTP message
above. Four were returned as benign. The two that were flagged have one thing in
common, and it is not that they mention a bank, because all six do. They are the
only two that ask the reader to log in.

That makes the weakness describable rather than mysterious. Nearly every scam in
the training data works by getting someone to log in or hand over a code, so the
model has learned to treat authentication language as the signal it is looking
for. A genuine message that uses the same words falls on the wrong side of that
line. Three things follow.

\textbf{It is a limitation, and this is not the only message it would affect.}
Two of six is not a measurement, but it is enough to say the behaviour is
systematic rather than accidental. Genuine login alerts, OTP notices, and
statement reminders are common messages, and the system will over-flag them. The
scores in Chapter~V were measured on generated messages, and this is what the
system does when it meets writing from outside that set.

\textbf{The mistake is in the safer direction.} The system is built to prefer a
false alarm over a missed scam, because the costs are not equal: a false alarm
wastes a minute of the user's time, while a scam called safe can cost them their
savings. A wrongly flagged genuine message is the acceptable failure. A scam the
system called benign would be the serious one, and that is the error this design
is arranged to avoid.

\textbf{The advice was still safe.} Even with the label wrong, every suggestion
protects the user: check the official app, do not share the code, call the bank
yourself. A wrong label attached to harmful advice would be a real defect. A
wrong label attached to advice that is safe to follow is a much smaller one, and
it is the direct result of the rule that keeps recommendations inside a fixed
safe set.

\subsection*{PhoBERT's Answer on the Same Message}

Qwen writes a full JSON answer for every message. PhoBERT does not: its raw output is four numbers, one per class, always in the same fixed order --- \texttt{bank\_impersonation}, \texttt{zalo\_social\_engineering}, \texttt{task\_scam}, \texttt{benign}. Whichever number is largest decides the label, a rule called \textit{argmax}. For illustration only, not a value recorded from an actual run, a pass over the scam message in Input 1 above might return \texttt{[4.82, -1.03, 0.61, -2.14]}; the largest value sits at the first position, so the label is \texttt{bank\_impersonation}.

Those four numbers are never shown to the user, and PhoBERT never produces the quoted evidence, the written explanation, or the recommendations that Qwen's answer carries. It returns the label and nothing else, which is why the comparison in Chapter~V covers only the one thing both models do.

\section{Exporting the Model}

The trained Qwen adapter was merged back into its base model and converted through \texttt{llama.cpp} \cite{gerganov2023llamacpp} into one Q8\_0 GGUF file of 4{,}280{,}403{,}232 bytes. It was then loaded twice, once independently, to confirm the exported file works.

Figure~\ref{fig:artifacts-on-disk} shows everything the two runs left on disk, the export included.

At runtime the analysis service normalises the message text, sends it to whichever model is configured, and returns the risk tier, threat label, quoted evidence, written explanation, and safe next steps. Nothing in this path needs an API key or an internet connection.

\section{Error Analysis and Adjustments}

Four problems shaped this project more than any of the successes, and each one changed how the next stage was built.

\textbf{Generation kept dying part-way through.} The first dataset pass ran for hours against an external API. When the provider stopped accepting requests mid-run, the job ended and took everything generated up to that point with it, because results were only written at the end. Two changes fixed it: the generator now backs off and retries instead of giving up on a refused request, and it writes results to disk as it goes. A failure now costs the last few minutes rather than the whole run.

\textbf{A large part of the generated data was unusable.} One class had been written as narration and others carried template leftovers. These were found by reading the output, not by any automatic check, which is the argument for reading generated data rather than trusting it.

\textbf{Neither ordinary LoRA nor a larger model was practical on this hardware.} The measurement run left almost no spare memory and pointed at an eighteen-hour schedule, and the 7B candidate needed roughly twice the memory of the 4B one before training was even considered. Rather than start an eighteen-hour run and hope, the project switched to QLoRA, which fits the card with room to spare.

\textbf{A save-path defect cost a full training run.} The first attempt at the full Qwen run reached real checkpoints, then two defects appeared in how output folders and validation files were named: the folder name left out the run ID, so a second run would have overwritten the first, and one code path rebuilt the saved file through the wrong Python type. The run was stopped on purpose and kept as a record. Nothing from it was carried into the final run, which restarted from step zero.
