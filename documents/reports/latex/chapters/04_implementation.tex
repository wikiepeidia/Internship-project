This chapter describes the implementation that produced the final dataset, the two locally trained models, and the offline analysis runtime. The implementation was designed around three constraints: seed-level data integrity, an 8~GiB laptop GPU, and evidence that could be checked after each long-running experiment. The current repository architecture was refactored after the terminal evaluation; consequently, the frozen experiment bundle remains the authority for the reported metrics, while the refactored source tree is the maintained implementation.

\section{Implemented System Boundary}

The installed application is \texttt{vnphish}. Its public commands are \texttt{analyze}, \texttt{doctor}, and \texttt{demo}. The analyze and demo paths share the \texttt{AnalysisRequest}/\texttt{AnalysisResult} contract, while doctor reports profile readiness separately through \texttt{DoctorStatus}. The maintained source tree is organized by domain rather than by experiment date:

\begin{quote}
\begin{verbatim}
src/
+-- core/                 # strict JSON, hashing and safe writes
+-- artifacts/            # model and result artifact readers
+-- config/               # local settings and profile selection
+-- data_pipeline/
|   +-- core/             # records, text, seed-safe splitting
|   +-- workflows/        # scraping, generation and judging
|   `-- migrations/       # reviewed one-off corpus repairs
+-- modeling/             # training, inference, evaluation ports
+-- runtime/              # CLI, service, analyzers, demo, rendering
+-- source_archiving/     # immutable source-closure operations
`-- model_adaptation/     # retained experiment compatibility layer
\end{verbatim}
\end{quote}

The active dependency graph contains 29 modules and 83 declared import edges and is acyclic. New code enters model training, inference, evaluation, and evidence handling through the domain-neutral \texttt{src.modeling} ports. The older model-adaptation modules remain behind explicit compatibility adapters because they are still needed to explain and verify the completed experiments. This separation avoids pretending that a later refactor generated earlier measurements.

The main model-adaptation command facade was reduced from 1{,}329 physical lines to 232 lines while preserving its 23-command compatibility contract. Similarly, an 886-line source-archiving utility was reduced to a 160-line facade over bounded contract, filesystem, and service modules. The refactor therefore improves navigation for maintenance and defence without rewriting the frozen producer source or metric artifacts.

\section{Dataset Construction and Repair}

Every record carries a \texttt{seed\_id}. Variants derived from one semantic scenario retain that identifier, and group-integrity splitting assigns the entire seed group to one partition. This is more restrictive than row-level random splitting, but it prevents paraphrases of one root scenario from appearing on both sides of an evaluation boundary. The promoted corpus contains 2{,}097 rows: 1{,}658 for training, 219 for validation, and 220 for terminal evaluation. The three seed sets are disjoint, and the largest seed contributes 7.9638\% of the corpus, below the declared 8\% cap.

The data work also retained failures rather than hiding them. Independent review detected systematic third-person narrative and scenario-framing artifacts in a synthetic Zalo social-engineering subset. The affected 240 retained records were replaced rather than relabelled as authentic messages. A controlled offline, model-assisted reconstruction started from 60 preserved semantic roots and produced five direct-message realizations per root. The root's \texttt{seed\_id} and its pre-existing split assignment were retained; non-Zalo records were unchanged. Schema, character-span, lexical and normalized-duplicate, label-support, seed-cap, and cross-split lineage checks all passed. Four reconstructed records were later quarantined by semantic convergence, leaving 296 reconstructed rows in the 297-row final Zalo class. This procedure made no external API call, but it remains synthetic reconstruction and is not presented as independently observed traffic.

The quality pipeline then joined 2{,}097 machine-judge verdicts: 1{,}561 exact-record carries and 536 newly judged final-delta records. A Vietnamese-fluent reviewer separately completed a 100-row stratified audit and a targeted 324-candidate mislabel triage. These artifacts are kept distinct because a partial human review cannot be described as complete manual annotation of the corpus.

\section{Resource-Gated Adaptation Strategy}

The selected generative model was \texttt{Qwen3-4B-Instruct-2507} \cite{qwen2025}. Ordinary LoRA \cite{hu2022lora} and 4-bit QLoRA \cite{dettmers2023qlora} were first measured in bounded probes on the same NVIDIA GeForce RTX~5050 Laptop GPU, which reports 8{,}151~MiB of device memory. The probes were feasibility experiments, not accuracy experiments, and their disposable adapters were deleted after verification.

\subsection{Ordinary-LoRA Probe}

The ordinary-LoRA retry retained 31 optimizer events: five excluded warm-up events and 26 measured events. It ran for 1{,}782.206~seconds (29~minutes 42.206~seconds), with a median measured step time of 53.274~seconds. Multiplying this incomplete-window median by the planned 1{,}245-step schedule gives an 18.42-hour compute-only estimate; the corresponding mean-step estimate is 18.88~hours. Neither value includes the full evaluation and checkpoint cadence, so neither is an observed training duration or a completion guarantee.

The run peaked at 7{,}902/8{,}151~MiB device VRAM and reached only 9~MiB minimum free VRAM. Peak system RAM used was 22{,}479{,}200{,}256~bytes on a 33{,}943{,}490{,}560-byte host. It completed optimizer work with finite losses and did \emph{not} produce a CUDA or system out-of-memory exception. The controller stopped with \texttt{parent\_controller\_error} before the 40-step evidence target, so the honest conclusion is practical resource pressure and insufficient headroom on this laptop, not that LoRA is impossible or that it OOMed. A 32~GB-class system-RAM host with more than 8~GB VRAM is therefore a practical recommendation for a reliable full run with headroom, not a benchmarked minimum specification.

\subsection{Genuine NF4 QLoRA Probe}

The separate QLoRA probe verified NF4 with double quantization, 252 \texttt{Linear4bit} modules, a frozen base model, and 504 trainable adapter tensors. It completed exactly five warm-up plus 40 measured optimizer steps. The measured median was 3.462389~seconds per step. Combining that median with one observed validation pass and one observed checkpoint save produced a projected 4{,}369.750-second schedule (72~minutes 49.750~seconds). This is an extrapolation from the bounded probe, not the wall-clock duration later observed for full training.

The QLoRA probe peaked at 7{,}516/8{,}151~MiB VRAM, retained 395~MiB minimum free VRAM, and used 22{,}136{,}381{,}440~bytes peak system RAM. It reached the exact evidence target without an OOM. Figure~\ref{fig:resource-probe-comparison} summarizes the measured resource evidence while keeping the projected durations visibly separate from observed execution.

\section{Full Local Model Training}

Both final models were trained locally from step zero with random seed 42 on the same 1{,}658-row training and 219-row validation identities. The 220-row terminal partition was not an input to training or checkpoint selection. The two validation runs are comparable for predictive quality because they use the same ordered validation cohort; their timing is not used for a speed claim because Qwen is a generative structured-output model whereas PhoBERT is a classification-head model.

\subsection{Qwen QLoRA}

The full Qwen run used the same genuine 4-bit NF4 configuration, three epochs, and 1{,}245 optimizer steps. Exact package identities were Python~3.13.13, PyTorch~2.12.0+cu132, Transformers~5.9.0, PEFT~0.19.1, and bitsandbytes~0.50.1. Validation checkpoints were selected under a predeclared safety gate rather than by terminal-evaluation performance. Checkpoint 200 was retained with validation accuracy 0.990868, macro F1 0.988515, zero invalid structured outputs, and zero risky-to-benign errors. The unrounded accuracy and macro F1 values are retained in Table~\ref{tab:qlora-config}.

An earlier full-run attempt reached useful intermediate evidence but exposed two implementation defects: the mutable output root omitted the run-ID segment, and a validation object was compared against canonical JSON in the wrong representation. It was deliberately interrupted and retained as failure evidence. No checkpoint from that attempt seeded the final run. After focused fixes, a clean request restarted from step zero and completed all 1{,}245 steps. This recovery is important because silently continuing from a structurally ambiguous work root would have made the final lineage harder to defend.

\subsection{PhoBERT Classification Baseline}

The Vietnamese encoder baseline uses \texttt{vinai/phobert-base-v2} with a four-logit sequence-classification head \cite{nguyen2020phobert}. It is a full, non-quantized classifier: the encoder and head are trained directly, with no LoRA, QLoRA, PEFT target modules, or generative parser. Vietnamese word segmentation is part of its deterministic preprocessing. The final local run used seed 42, three epochs, and 312 optimizer steps; checkpoint 100 was retained with validation accuracy 0.9863013699, macro F1 0.9848929140, zero invalid outputs, and zero risky-to-benign errors.

Superseded attempts exposed telemetry and finalization defects. The successful training evidence was preserved, and telemetry was recovered through a separately verified recovery path without changing predictions, metrics, or selected checkpoint identity. This distinction prevents operational evidence repair from being mistaken for model retraining or metric recomputation.

\section{Artifact Export and Runtime}

The selected Qwen adapter was merged with the pinned base and converted through \texttt{llama.cpp} \cite{gerganov2023llamacpp} into one Q8\_0 GGUF file. The verified artifact is 4{,}280{,}403{,}232~bytes with SHA-256
\begin{center}
\small\texttt{457f6f92d36a7d54da9916fd80a4028dcd055a653a015c4877370a0fea4d18ab}.
\end{center}
Both the original conversion environment and an independent CPU load smoke accepted the artifact before its portable receipt was registered. PhoBERT remains a Transformers sequence-classification bundle and was \emph{not} converted to GGUF.

At runtime, the analyze and demo paths use \texttt{AnalysisRequest} and \texttt{AnalysisResult} for the public analysis contract. The service normalizes text, selects an explicit local profile, dispatches to a heuristic, GGUF, or accelerated-local analyzer, and returns a structured risk tier, threat labels, grounded cues, and safety recommendations. \texttt{vnphish doctor} reports selected-profile and artifact readiness through \texttt{DoctorStatus} before analysis. No provider credential is required for the offline runtime.

\section{Evidence and Failure-Recovery Design}

Each full run retains resolved configuration, package and CUDA identity, append-only events, system/GPU telemetry, checkpoint candidates, raw ordered validation predictions, metrics, selected-model hashes, and graph provenance. Both canonical loss plots were reproduced byte-for-byte from their retained normalized data during verification. This evidence design is what distinguishes a completed local experiment from a copied model repository: the report can bind configuration, execution, selection, conversion, and evaluation to specific artifacts.

The terminal evaluation similarly produced one frozen two-model export. The metric-authority manifest and mandatory provenance correction are bound by the following identities:

\section{Current Architecture Review Status}

The refactor has measurable benefits: the active graph is acyclic, command compatibility is explicit, historical implementations have named owners, and exact bounded architecture tests passed. It is nevertheless not correct to describe the architecture work as fully clean. The latest adversarial review records six open critical issues: completeness of the guarded filesystem boundary, undeclared pre-created native handles, incomplete collection-time attestation, compound-command and callable-alias route discovery, loopback demo Host/Origin/content-type validation, and terminal control-sequence sanitization. Three warnings additionally cover shell-chain scanning, host/port binding validation, and the test runner's dependence on disabling pytest plugin autoload.

These findings do not change the already frozen model metrics, but they block a claim that the maintained architecture is production-ready. They are reported here because implementation quality includes known failure boundaries as well as completed functionality.
