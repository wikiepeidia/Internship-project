This chapter summarizes the background that motivates the thesis design. The focus is on Vietnamese financial phishing patterns, local privacy constraints, explainability as a user-facing safety requirement, and the trade-offs involved in running open-weight models on local hardware.

\section{Vietnamese Financial Phishing Context}
The target domain in this thesis is Vietnamese financial phishing and social-engineering detection rather than generic spam filtering. The main in-scope threat classes are bank impersonation, social-engineering messages on common messaging platforms, and lightweight task scams that pressure the victim into a fast transfer or credential disclosure. This narrow focus matters because the dangerous signals are often contextual, platform-specific, and culturally localized rather than purely lexical \cite{pham2016vietnamese}.

\textbf{In-scope threat classes:} bank impersonation via SMS or chat, social-engineering messages on Zalo and similar platforms, and task scams that create artificial urgency. \textbf{Out of scope for this version:} image-based phishing, QR-code fraud, voice calls, deepfake audio or video, malware-carrying APKs, and any content requiring OCR or multimodal processing. This boundary is deliberate; it keeps the v1 system focused on the text-only privacy case and avoids overstating what the current evaluation supports.

\section{Local Inference as a Privacy Control}
Suspicious financial messages often contain names, phone numbers, banking details, and account-recovery prompts. For that reason, local inference is treated here as a privacy control rather than only a deployment preference \cite{nist2026privacyframework}. The runtime design therefore focuses on text-only local analysis and avoids any requirement to upload raw content to a remote service during ordinary use. The same principle also shapes the deployment strategy: one profile is optimized for lightweight GGUF inference on consumer hardware, while another profile supports stronger local acceleration when better hardware is available.

Cloud-based API alternatives present several practical problems for this use case. A user who pastes a suspicious banking message into a general-purpose chatbot transfers OTP codes, account numbers, and personal identifiers to a third-party service. API products that advertise data privacy often retain inputs for safety monitoring or limit zero-retention policies to approved enterprise accounts, so ordinary users have no strong guarantee that sensitive message content is not logged.

Beyond passive logging risk, documented incidents show that cloud API deployments can expose sensitive user data through active security failures. In March 2023, OpenAI disclosed a Redis caching bug that exposed the chat history, payment card details, and account information of approximately 1.2\% of ChatGPT Plus subscribers to other users for a nine-hour window \cite{openai2023breach}. A similar failure of the local-only design philosophy occurred at Samsung Semiconductor in 2023: engineers pasted confidential chip design source code and internal meeting notes into ChatGPT to assist with code review tasks, only to discover that these inputs were stored on OpenAI's servers and could potentially be used for model training \cite{bloomberg2023samsung}. Both incidents demonstrate that sensitive content submitted to a cloud API --- whether through a security failure or routine service operation --- can reach unauthorized parties. For a financial phishing detection tool whose inputs are OTP codes, bank account numbers, and social-engineering messages, this risk class is structurally more serious than domain hallucination or off-task compliance: the user's sensitive financial data is precisely the content that must not reach a third-party server.

\section{Explainability and User-Facing Safety}
Explainability is not treated as a cosmetic add-on. The system is designed to return one risk tier, one or more in-scope threat labels for risky inputs, grounded suspicious cues taken from the analyzed text, and recommendations that stay safe for the user. In practice, the system should report cues taken from the message text itself rather than relying on model confidence scores alone. The design of this layer takes the structured evidence requirement as a starting point rather than an afterthought \cite{rjoub2023surveyxai}. A related approach, EXPLICATE, shows that grounding phishing explanations in text-level evidence improves user trust in the output \cite{lim2025explicate}.

Explainability also serves a second purpose: it lets the user make an informed decision without needing to forward the suspicious message to an external service for a second opinion. For Vietnamese financial phishing, asking a cloud chatbot to verify a suspicious message re-introduces the exact data-leak risk that local inference is designed to prevent. A local system that explains its reasoning therefore provides both the detection verdict and its justification without any external dependency, which makes the explanation layer a privacy control as much as a usability feature.

\section{Open-Weight Local Models and Deployment Trade-offs}
The modeling strategy is based on parameter-efficient adaptation of an open Qwen family \cite{qwen2025} rather than full-scale retraining. Modern deep learning models applied to text classification \cite{minaee2021text} typically require substantial hardware for full fine-tuning; parameter-efficient methods such as LoRA \cite{hu2022lora} and QLoRA \cite{dettmers2023qlora} address this by training only a small set of rank-decomposed weight updates, making adaptation feasible on consumer GPU hardware. A 4B-primary path was chosen to stay within the intended hardware envelope after a pilot comparison of three candidates, including a 7B model, showed that the 4B family provided a more reliable fit on the target laptop hardware without sacrificing the recall-first selection criterion. The deployment design then separates a GGUF baseline for laptop-class local inference from an accelerated local path for stronger GPU hardware. This split is important because model choice, artifact conversion, and runtime delivery affect both usability and the credibility of any real local-first deployment claim.

The viability of this deployment pattern is supported by recent industry practice. Google began shipping a 4~GB Gemini Nano model to ordinary Chrome browser users' devices in 2024--2025, running local summarization, scam detection, and text-assistance features without sending content to remote servers \cite{cyberinsider2026geminanano}. This demonstrates that consumer hardware has reached the point where billion-parameter quantized models can run on-device without requiring dedicated GPU hardware. The 4B GGUF model used in this thesis targets the same hardware class and the same privacy rationale, and it could in principle be embedded in a similar browser-resident or application-resident pipeline in future work.

\section{Evaluation Priorities}
The evaluation strategy in this thesis gives special weight to recall on harmful scam classes because missing a dangerous phishing attempt is generally more costly than generating a cautious false alarm. Overall F1 scores remain useful summary statistics, but they are not sufficient on their own. Per-label recall and explanation quality matter directly because they determine whether the system can support a trustworthy user-facing decision.
